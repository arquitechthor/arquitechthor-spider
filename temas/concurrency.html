Qué es

La concurrencia es la capacidad de un programa de llevar varias tareas a la vez: atender a dos usuarios, leer de la red mientras calcula, esperar a una base de datos sin quedarse parado. En Java, cada tarea que avanza por su cuenta es un hilo (Thread), y un programa con varios es multihilo.

No es lo mismo que el paralelismo. Concurrencia es organizar varias tareas que progresan a la vez; paralelismo es ejecutarlas literalmente al mismo tiempo en varios núcleos de la CPU. Un servidor web es concurrente aunque tenga un solo núcleo; ordenar un millón de números repartiéndolos entre ocho núcleos es paralelo.

Por qué importa

  • Todo servidor es concurrente. Spring Boot atiende cada petición en su propio hilo: aunque no escribas ni un Thread, tu código se ejecuta en varios a la vez.
  • Los fallos son los peores. Un error de concurrencia aparece una vez de cada mil, desaparece al depurarlo y no se reproduce en las pruebas. Es más barato evitarlo con diseño que perseguirlo.
  • La mayoría de los programas esperan. Una petición típica pasa casi todo su tiempo esperando a la base de datos o a otro servicio. Saber esperar sin desperdiciar hilos es lo que permite atender a miles de usuarios con pocos recursos, y es lo que resuelven los hilos virtuales de Java 21.

Vocabulario para empezar

  • Hilo de plataforma: el hilo clásico de Java, que es un hilo del sistema operativo. Es caro: cada uno reserva memoria para su pila y crearlo lleva su tiempo, así que un programa tiene, como mucho, unos miles.
  • Hilo virtual: un hilo que gestiona la propia JVM (Java 21). Cuesta casi nada, y puede haber millones.
  • Bloquearse: que un hilo se quede parado esperando algo (una respuesta, un fichero, un candado libre) sin avanzar.
  • Estado compartido: datos que varios hilos pueden leer y modificar, como un atributo de un objeto que usan todos. Es el origen de casi todos los problemas.
  • Condición de carrera: un fallo cuyo resultado depende de qué hilo llega antes. El programa funciona casi siempre y falla cuando el orden es otro.
  • Sección crítica: un trozo de código que solo debe ejecutar un hilo a la vez porque toca estado compartido.
  • Seguro para hilos (thread-safe): una clase que se comporta bien aunque la usen varios hilos a la vez sin coordinarse entre ellos.

Los tres problemas del estado compartido

Atomicidad: operaciones que parecen una y son tres

contador++ parece una sola operación, pero son tres: leer el valor, sumarle uno y escribirlo. Si dos hilos leen a la vez el 5, los dos escriben 6, y se ha perdido una suma.

class Visitas {
    private int total;
    void sumar() { total++; }   // dos hilos a la vez pueden perder sumas
}

Visibilidad: lo que un hilo escribe, otro puede no verlo

Para ir más rápido, cada núcleo trabaja con copias en su caché, y el compilador y la CPU reordenan instrucciones. Sin una instrucción que obligue a sincronizar, un hilo puede no ver nunca lo que escribió otro:

private boolean parar;            // sin volatile

void trabajar() {
    while (!parar) { … }          // puede no enterarse nunca de que parar es true
}
void detener() { parar = true; }  // lo llama otro hilo

Orden: el modelo de memoria de Java

El modelo de memoria de Java (JMM) define cuándo lo que escribe un hilo es visible para otro. Su idea central es la relación happens-before («ocurre antes»): soltar un candado ocurre antes que el siguiente que lo coja, escribir un campo volatile ocurre antes que las lecturas posteriores de ese campo, y arrancar un hilo ocurre antes que todo lo que hace ese hilo. Si dos accesos no están unidos por una de estas relaciones, no hay garantías.

Las herramientas básicas

  • synchronized: un método o bloque synchronized solo lo ejecuta un hilo a la vez por objeto, y además garantiza la visibilidad: quien entra ve todo lo que hizo el anterior. Es reentrante (el hilo que ya lo tiene puede volver a entrar).
  • volatile: garantiza que toda lectura ve la última escritura de ese campo. No hace atómico contador++: sirve para avisos (un boolean parar) y para publicar un objeto ya construido.
  • Inmutabilidad: un objeto que no cambia, como un record con campos que no cambian, se puede compartir entre hilos sin ninguna protección. Es la mejor defensa: sin escrituras no hay carreras.
  • Confinamiento: datos que solo usa un hilo (variables locales, un objeto creado y usado dentro de la misma tarea) no necesitan protección.
class Visitas {
    private int total;
    synchronized void sumar() { total++; }   // ya no se pierden sumas
    synchronized int total() { return total; }
}

java.util.concurrent: no reinventar la rueda

Desde Java 5, el paquete java.util.concurrent trae piezas probadas que casi siempre son mejores que coordinar hilos a mano con synchronized, wait y notify:

  • Ejecutores (ExecutorService): reciben tareas y las reparten entre hilos; submit devuelve un Future para recoger el resultado. Desde Java 19 se cierran con try-con-recursos, que espera a que acaben las tareas.
  • CompletableFuture: un resultado que llegará más tarde y al que se encadenan pasos (thenApply, thenCompose, exceptionally) sin bloquear.
  • Variables atómicas (AtomicInteger, AtomicReference, LongAdder): operaciones como incrementar o «cambia si sigue valiendo X» en un solo paso, sin candados. LongAdder rinde mejor que AtomicLong en contadores que muchos hilos incrementan a la vez.
  • Colecciones concurrentes: ConcurrentHashMap (con merge y compute atómicos), ConcurrentLinkedQueue y las BlockingQueue, cuyas operaciones esperan si la cola está vacía (o llena): la base del patrón productor-consumidor.
  • Candados explícitos (ReentrantLock, ReadWriteLock): como synchronized, pero con intento con tiempo límite (tryLock) y varios lectores a la vez.
  • Sincronizadores: Semaphore (un número fijo de permisos: quien no consigue uno, espera), CountDownLatch (esperar a que N cosas terminen) y otros.
Map<String, Integer> visitas = new ConcurrentHashMap<>();
visitas.merge(pagina, 1, Integer::sum);   // sumar uno es atómico: nunca se pierde una visita

Interrumpir y cancelar

En Java no se puede detener un hilo desde fuera a la fuerza: se le pide que pare con interrupt(), y el hilo lo atiende. Si estaba esperando (sleep, join, una cola), la espera termina con InterruptedException. Tragarse esa excepción es un error clásico: o se propaga, o se vuelve a marcar el hilo como interrumpido para que el código de más arriba se entere.

try {
    var tarea = cola.take();
    procesar(tarea);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restaurar el aviso y salir
    return;
}

Hilos virtuales (Java 21)

Un hilo virtual corre encima de un hilo de plataforma prestado. Cuando se bloquea esperando (red, disco, una cola), la JVM lo aparta y presta ese hilo de plataforma a otro hilo virtual; cuando llega lo que esperaba, continúa donde estaba. Así se escribe código bloqueante sencillo, de arriba abajo, y aun así unos pocos hilos reales atienden miles de tareas.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var pedido : pedidos) {
        executor.submit(() -> enviar(pedido));   // un hilo virtual por pedido
    }
}   // aquí ya han terminado todos

Thread.ofVirtual().name("lector").start(this::leer);   // o uno suelto
  • Brillan en tareas que esperan (servicios web, acceso a datos, procesos externos). En cálculo puro no ganan nada: los núcleos son los que son.
  • No se agrupan en pools. Se crea uno por tarea. Para limitar cuántas tareas usan a la vez un recurso escaso (conexiones, una API con cuota), se usa un Semaphore.
  • synchronized ya no estorba. Hasta Java 23, bloquearse dentro de un bloque synchronized dejaba «clavado» el hilo de plataforma; desde Java 24 ya no.
  • ThreadLocal funciona, pero pesa. Con millones de hilos, una copia por hilo gasta mucha memoria. ScopedValue (definitivo en Java 25) comparte un valor de solo lectura con todo lo que se llama desde un bloque, sin ese coste.
  • En Spring Boot basta con spring.threads.virtual.enabled=true para atender las peticiones con hilos virtuales.

Las novedades de cada versión de Java se cuentan en Java moderno.

Concurrencia estructurada (preview)

Lanzar varias subtareas en paralelo con un ejecutor deja preguntas abiertas: si una falla, ¿quién cancela las demás?, ¿y si el que esperaba se va? La concurrencia estructurada (StructuredTaskScope, en vista previa en Java 25 y 26) trata las subtareas como un bloque: empiezan y terminan dentro de él, y si una falla, el resto se cancela. Al salir del bloque no queda ningún hilo suelto.

try (var scope = StructuredTaskScope.open()) {        // preview: --enable-preview
    var usuario = scope.fork(() -> buscarUsuario(id));
    var pedidos = scope.fork(() -> buscarPedidos(id));
    scope.join();                                     // si una falla, cancela la otra y lanza la excepción
    return new Resumen(usuario.get(), pedidos.get());
}

Interbloqueos y otros peligros

  • Interbloqueo (deadlock): el hilo A tiene el candado 1 y espera el 2; el hilo B tiene el 2 y espera el 1. Ninguno avanza nunca. Se evita cogiendo siempre los candados en el mismo orden, o con tryLock y tiempo límite.
  • Inanición (starvation): un hilo nunca consigue el recurso porque otros se le adelantan siempre. Los candados y semáforos justos (new Semaphore(n, true)) atienden por orden de llegada.
  • Bloqueo activo (livelock): los hilos no están parados, pero se ceden el paso unos a otros sin fin y nadie progresa.

Caso real: Kopi Chess

Kopi Chess (código público, Java 25 y Spring Boot) juega y analiza partidas con Stockfish, un motor de ajedrez que es un programa aparte con el que se habla por texto (protocolo UCI). Tiene casi todas las situaciones de esta ficha: esperar a un proceso externo, repartir un recurso caro, trabajos en segundo plano y una conexión que hay que compartir.

Leer de Stockfish: un hilo virtual y una cola

Stockfish contesta cuando quiere y con muchas líneas. Leer su salida es bloqueante (readLine espera hasta que llega una línea), así que cada motor tiene un hilo virtual que solo lee y deja cada línea en una BlockingQueue. Quien espera una respuesta la saca de la cola con tiempo límite: si el motor se cuelga, salta un error en lugar de esperar para siempre. Es el patrón productor-consumidor:

private final BlockingQueue<String> lines = new LinkedBlockingQueue<>();

private UciProcess(Process process) {
    …
    Thread.ofVirtual().name("uci-reader-" + process.pid()).start(this::readOutput);
}

private void readOutput() {          // productor: el hilo virtual
    … while ((line = output.readLine()) != null) { lines.add(line); }
}

public String receive(Duration timeout) {   // consumidor: quien pregunta
    var line = lines.poll(timeout.toNanos(), TimeUnit.NANOSECONDS);
    if (line == null) throw new UciException("No answer from the engine within " + timeout);
    …
}

Cuando el proceso muere, el lector mete en la cola una marca de fin para despertar a quien espere. Al capturar InterruptedException, el código vuelve a marcar el hilo como interrumpido, como se recomienda arriba (UciProcess.java).

Repartir motores: un semáforo justo

Cada Stockfish gasta CPU y memoria, así que solo puede haber unos pocos, y cada uno se presta a una sola tarea a la vez. El pool de motores combina varias piezas de java.util.concurrent:

private final Semaphore permits;                       // new Semaphore(size, true): justo
private final ConcurrentLinkedQueue<E> idle = new ConcurrentLinkedQueue<>();
private final LongAdder discarded = new LongAdder();   // motores reiniciados (una métrica)
private volatile boolean closed;

<T> T withEngine(Function<E, T> work) {
    acquire();                     // tryAcquire con tiempo límite: error si no hay motor libre a tiempo
    try {
        var engine = idleOrNew();  // uno libre que siga vivo, o uno nuevo
        … work.apply(engine) …     // si falla, el motor se descarta y se cuenta
    } finally {
        permits.release();         // el permiso se devuelve pase lo que pase
    }
}

El semáforo limita cuántos motores se usan a la vez y, por ser justo, atiende las peticiones por orden de llegada. La cola guarda los motores libres sin candados, LongAdder cuenta los reinicios y volatile hace que todos los hilos vean a la vez que el pool se ha cerrado (EnginePool.java).

Trabajos en segundo plano: hilos virtuales que se paran bien

El análisis de partidas se hace de fondo: unos pocos hilos virtuales cogen el siguiente trabajo de la cola (una tabla de PostgreSQL) una y otra vez, y descansan un momento cuando no hay ninguno. Para parar, un aviso volatile, una interrupción para despertar a los que duermen y una espera con tiempo límite a que terminen:

private volatile boolean running;

public synchronized void start() {
    running = true;
    for (int i = 1; i <= properties.workers(); i++) {
        threads.add(Thread.ofVirtual().name("analysis-worker-" + i).start(this::work));
    }
}

public synchronized void stop() {
    running = false;                     // el bucle while (running) termina
    threads.forEach(Thread::interrupt);  // y quien duerme se despierta
    for (var thread : threads) thread.join(Duration.ofSeconds(5));
    …
}

Un trabajo que se queda a medias sigue marcado como «en curso» y se recupera en el siguiente arranque (AnalysisWorker.java). Que dos trabajadores no cojan el mismo trabajo lo garantiza la base de datos, no Java (ADR-007).

Partidas online: synchronized donde se cruzan dos hilos

Una partida contra un amigo se mantiene al día con un servidor intermedio, el relé. Dos hilos pueden tocar la misma partida a la vez: el que sincroniza de fondo con el relé y el de la petición del jugador que mueve. Todos los métodos que leen y cambian ese estado son synchronized, de modo que una jugada nunca se mezcla con una sincronización a medias (OnlineGames.java). Además, guardar una partida usa bloqueo optimista: cada partida tiene un número de versión, y si otro la guardó entre medias, la segunda escritura falla en lugar de pisar a la primera.

Una conexión, muchos hilos: envíos encadenados

La conexión WebSocket con el relé solo admite un envío a la vez, pero quieren enviar varios hilos (las respuestas, el latido cada cinco minutos…). Cada envío se encadena al anterior con CompletableFuture, sin bloquear a nadie; y cada petición que llega se atiende en su propio hilo virtual (pensar la jugada de un bot tarda), nunca en el hilo de la conexión:

private final ExecutorService requests = Executors.newVirtualThreadPerTaskExecutor();
private CompletableFuture<?> lastSend = CompletableFuture.completedFuture(null);

private synchronized void send(WebSocket to, String text) {
    lastSend = lastSend.handle((_, _) -> null)               // pase lo que pase con el anterior…
            .thenCompose(_ -> to.sendText(text, true))       // …envía este cuando termine
            .exceptionally(error -> { to.abort(); return null; });
}

(RelayWebSocket.java)

Concurrencia estructurada, en el laboratorio

Como está en vista previa, Kopi Chess la usa solo en su módulo de pruebas kopi-labs: analizar varias posiciones a la vez, cada una en su hilo virtual, de forma que si una falla las demás se cancelan y no queda ningún hilo suelto (PositionBatchAnalyser.java).

Errores frecuentes

  • Creer que volatile hace atómico contador++: solo garantiza que se ve el último valor. Para contar, AtomicInteger, LongAdder o synchronized.
  • Sincronizar la escritura y no la lectura: si el getter no está sincronizado, quien lee puede ver un valor viejo. Los dos lados deben usar el mismo candado.
  • Comprobar y luego actuar en dos pasos: if (!mapa.containsKey(k)) mapa.put(k, v) no es atómico ni con un ConcurrentHashMap. Usa putIfAbsent, computeIfAbsent o merge.
  • Tragarse InterruptedException: con un catch vacío el hilo ya no sabe que le pidieron parar, y el programa no se cierra bien. Restaura la marca o propaga la excepción.
  • Esperar sin límite: take(), join() o get() sin tiempo máximo cuelgan el hilo si el otro lado muere. En llamadas a procesos o servicios externos, pon siempre un tiempo límite.
  • Usar streams paralelos para esperar: parallelStream() reparte el trabajo en un pool común con tantos hilos como núcleos; si las tareas esperan a la red, lo bloquean para toda la aplicación. Es para cálculo, no para esperas.
  • Hilos virtuales en un pool fijo: anula su ventaja. Uno por tarea y, si hay que limitar, un semáforo.
  • Compartir lo que no hace falta: antes de proteger un estado, pregúntate si puede ser inmutable o local a una tarea. El estado que no se comparte no necesita candados.
