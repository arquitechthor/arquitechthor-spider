Qué es

Kubernetes es un sistema para ejecutar aplicaciones en contenedores sobre un grupo de máquinas (un clúster) y mantenerlas como tú has descrito: cuántas copias, con qué imagen, con qué configuración y cómo se llega a ellas. Si un contenedor muere, lo reinicia; si una máquina cae, mueve su trabajo a otra; si despliegas una versión nueva, sustituye las copias poco a poco.

Lo creó Google a partir de su experiencia interna, se publicó como software libre en 2014 y hoy lo mantiene la Cloud Native Computing Foundation. Se suele abreviar k8s (una k, ocho letras y una s). Todos los grandes proveedores lo ofrecen gestionado: Amazon EKS, Google GKE y Azure AKS.

Vocabulario para empezar

  • Contenedor e imagen: una imagen es un paquete con la aplicación y todo lo que necesita; un contenedor es esa imagen en marcha, aislada. Ver Docker.
  • Declarativo: no das órdenes («arranca tres copias»), describes el estado deseado («quiero tres copias») en un fichero YAML, y Kubernetes trabaja continuamente para que la realidad coincida.
  • Nodo: cada máquina (física o virtual) del clúster donde se ejecutan los contenedores.

Por qué importa

Con unos pocos servicios se puede desplegar a mano en servidores. Con decenas de microservicios, varios entornos y despliegues diarios, hace falta algo que decida dónde corre cada cosa, la reinicie si falla, la escale con la carga y despliegue sin cortar el servicio. Kubernetes se ha convertido en el estándar para eso. Aunque como desarrollador no administres el clúster, tu servicio vive en él: entender sus piezas es lo que te permite leer por qué no arranca, por qué se reinicia o por qué no recibe tráfico.

Conceptos clave

  • Pod: la unidad mínima: uno o varios contenedores que comparten red y almacenamiento. Los pods son efímeros; no se crean a mano, los crea un controlador.
  • Deployment: describe una aplicación sin estado: imagen, número de réplicas y estrategia de actualización. Por debajo usa un ReplicaSet, que mantiene el número de pods. Al cambiar la imagen, hace una actualización progresiva y permite volver atrás.
  • Service: un nombre y una dirección estables para un grupo de pods (que cambian de IP al reiniciarse). Reparte el tráfico entre ellos.
  • Ingress y Gateway API: reglas para que el tráfico de fuera del clúster (por dominio y ruta) llegue al Service correcto. Gateway API es la evolución más moderna.
  • ConfigMap y Secret: configuración separada de la imagen, que el pod recibe como variables de entorno o ficheros. Los Secret son para contraseñas y claves (y conviene cifrarlos o traerlos de un gestor de secretos externo).
  • Namespace: una partición lógica del clúster (por equipo o por entorno) con sus propios nombres, permisos y cuotas.
  • Sondas (probes): liveness (¿está vivo? si no, se reinicia), readiness (¿puede recibir tráfico? si no, se saca del Service) y startup (da tiempo a aplicaciones que tardan en arrancar).
  • Requests y limits: la CPU y memoria que el pod reserva y el máximo que puede usar. Pasarse del límite de memoria mata el contenedor (OOMKilled).
  • Job y CronJob: tareas que se ejecutan hasta terminar, una vez o con un horario (como un cron), por ejemplo una sincronización nocturna.
  • HorizontalPodAutoscaler: sube o baja el número de réplicas según el uso de CPU u otras métricas.

En la práctica

Un Deployment mínimo de un servicio Java, con dos réplicas, sondas y límites:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalogo
spec:
  replicas: 2
  selector:
    matchLabels: { app: catalogo }
  template:
    metadata:
      labels: { app: catalogo }
    spec:
      containers:
        - name: catalogo
          image: registro.ejemplo.com/catalogo:1.4.2
          ports: [{ containerPort: 8080 }]
          envFrom: [{ configMapRef: { name: catalogo-config } }]
          readinessProbe: { httpGet: { path: /q/health/ready, port: 8080 } }
          livenessProbe:  { httpGet: { path: /q/health/live,  port: 8080 } }
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits:   { memory: 768Mi }

Los comandos de kubectl que más se usan para investigar un servicio:

kubectl get pods -n mi-equipo                  # estado y reinicios
kubectl describe pod catalogo-7d9f-abcde        # eventos: imagen no encontrada, sonda fallida, OOMKilled
kubectl logs catalogo-7d9f-abcde --previous     # logs del contenedor que acaba de morir
kubectl rollout history deployment/catalogo     # versiones desplegadas
kubectl rollout undo deployment/catalogo        # volver a la anterior

En muchas empresas nadie aplica estos ficheros a mano: se usa GitOps. Los manifiestos viven en un repositorio y una herramienta como Argo CD o Flux sincroniza el clúster con lo que hay en Git. Para desplegar, se cambia el repositorio (por ejemplo, la etiqueta de la imagen). Los manifiestos suelen generarse con Helm o Kustomize para no repetirlos por entorno.

Errores frecuentes

  • Etiqueta latest en la imagen: no sabes qué versión corre y un reinicio puede traer otra. Usa versiones o el resumen (digest) de la imagen.
  • Sin sonda de readiness: el pod recibe tráfico antes de estar listo y los primeros usuarios reciben errores en cada despliegue.
  • Liveness que depende de otros servicios: si la base de datos cae, Kubernetes reinicia todos tus pods en bucle y no arregla nada. La liveness solo comprueba el propio proceso.
  • Límite de memoria por debajo de lo que usa la JVM: el contenedor muere con OOMKilled. Ajusta el límite y la memoria máxima de la JVM a la vez.
  • Cambios a mano en un clúster con GitOps: la herramienta los deshace en la siguiente sincronización. Cambia el repositorio.
  • Despliegues que se pisan: si dos ramas o dos procesos actualizan el mismo Deployment, gana el último y el entorno deja de tener lo que creías. Antes de probar, comprueba qué imagen corre de verdad (kubectl get deployment -o wide).
  • Secretos en un ConfigMap o en la imagen: cualquiera con acceso los lee. Usa Secret o un gestor de secretos.
