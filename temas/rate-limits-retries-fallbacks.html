Qué es

Esta ficha reúne las técnicas para que una aplicación que llama a modelos de lenguaje siga funcionando cuando la API falla, va lenta o te frena: respetar los límites de uso (rate limits), reintentar bien lo que merece reintentarse y tener un plan B (fallback) cuando no hay manera.

Son los mismos patrones de resiliencia de cualquier llamada remota, con particularidades: las llamadas a un LLM tardan segundos, cuestan dinero por token y fallan más que una API tradicional.

Vocabulario para empezar

  • Límite de uso: lo máximo que el proveedor te deja consumir por minuto, medido en peticiones y en tokens (de entrada y de salida). Superarlo devuelve un error 429.
  • Código de estado HTTP: el número con el que la API dice cómo fue la petición: 2xx bien, 4xx culpa de la petición (400 mal formada, 401 sin permiso, 429 demasiadas), 5xx culpa del servidor.
  • Idempotente: una operación que se puede repetir sin efectos extra. Ver idempotencia.

Por qué importa

Un servicio con IA depende de un tercero que a veces está saturado (Anthropic devuelve un 529 cuando sus servidores están sobrecargados), que te limita en horas punta y que puede tardar 30 segundos en una respuesta larga. Si cada fallo llega tal cual al usuario como un error genérico, la funcionalidad parece rota aunque el 95 % de las llamadas vaya bien. Y si se reintenta mal (de golpe, sin esperar, todos los clientes a la vez), se agrava la saturación que provocó el fallo.

Conceptos clave

  • Qué se reintenta: 429, 5xx (incluido 529) y errores de red o tiempos de espera. No se reintenta lo que va a fallar igual: 400 (petición mal formada, contexto demasiado largo, contenido bloqueado por un filtro), 401 o 403.
  • Espera exponencial con jitter: esperar 1 s, 2 s, 4 s… y añadir a cada espera un componente aleatorio para que miles de clientes no reintenten en el mismo instante. Si la API manda la cabecera Retry-After, respétala.
  • Pocos reintentos: dos o tres, no diez. Cada reintento de una llamada a un LLM son segundos de espera para el usuario.
  • Presupuesto de tiempo de toda la cadena: si delante de tu servicio hay un balanceador o un gateway que corta a los 30 segundos, de nada sirve que tu cliente espere 60 y reintente. Fija los tiempos de espera de dentro hacia fuera, cada uno menor que el de la capa anterior.
  • Fallback: qué hacer cuando no hay respuesta: otro modelo del mismo proveedor (más pequeño o en otra región), otro proveedor, una respuesta en caché, un resultado degradado («no he podido analizarlo, inténtalo de nuevo») o pasar el caso a una persona.
  • Circuit breaker: si un proveedor falla una y otra vez, dejar de llamarlo un rato y usar directamente el plan B, en lugar de que cada usuario espere su propio tiempo de espera.
  • Error controlado: distinguir en la respuesta un «el modelo no lo ha entendido» de un «el proveedor no está disponible», y no enseñar nunca al usuario el mensaje crudo del proveedor.
  • Gastar menos para chocar menos: respuestas más cortas, contextos más pequeños, caché de prompts y modelos más pequeños para tareas sencillas reducen tokens y, con ellos, los 429.

En la práctica

Un reintento con espera exponencial y jitter, sin bibliotecas, solo para errores que lo merecen:

Respuesta llamarConReintentos(Peticion p) {
    int intentos = 3;
    for (int i = 1; ; i++) {
        try {
            return cliente.llamar(p);
        } catch (ApiException e) {
            boolean reintentable = e.status() == 429 || e.status() >= 500;
            if (!reintentable || i == intentos) {
                throw e;
            }
            long base = e.retryAfterMillis().orElse(1000L * (1L << (i - 1)));
            long espera = base / 2 + ThreadLocalRandom.current().nextLong(base / 2 + 1);
            dormir(espera);
        }
    }
}

En la práctica rara vez se escribe a mano: bibliotecas como Resilience4j, SmallRye Fault Tolerance (en Quarkus, con @Retry, @Timeout, @CircuitBreaker y @Fallback) o los propios clientes de LangChain4j (opción maxRetries) ya lo traen. Lo importante es decidir qué errores entran, cuántas veces y con qué tiempo total.

Errores frecuentes

  • Reintentar un 400: el filtro de contenido o una petición demasiado larga van a fallar igual; solo gastas tiempo. Trátalo como respuesta controlada.
  • Reintentos en varias capas: si el cliente reintenta 3 veces, el servicio otras 3 y el que llama otras 3, un fallo se convierte en 27 llamadas. Reintenta en un solo sitio.
  • Tiempo de espera mayor que el de la capa de fuera: el usuario recibe un 504 del gateway mientras tu servicio sigue esperando al modelo.
  • Fallback que cambia el comportamiento sin avisar: un modelo de respaldo más pequeño puede responder distinto. Mídelo también con evals.
  • Tratar un fallo como «sin resultado»: si el modelo no responde, no es lo mismo que si respondió que no hay nada. Confundirlos puede aplicar una decisión a más casos de los debidos.
  • No mirar los límites hasta producción: con muchos usuarios simultáneos, los límites por minuto se alcanzan enseguida. Revísalos y pide ampliación antes de lanzar.
