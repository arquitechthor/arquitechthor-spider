Qué es

La arquitectura limpia (Clean Architecture) es una forma de organizar una aplicación en círculos concéntricos: en el centro, las reglas de negocio; alrededor, los casos de uso; después, el código que traduce entre la aplicación y el exterior; y por fuera, los frameworks, la base de datos y la web. La propuso Robert C. Martin («Uncle Bob») en un artículo de 2012, que desarrolló después en su libro Clean Architecture (2017).

No partía de cero: el propio artículo la presenta como un intento de unir en una sola idea varias propuestas que se parecían mucho, entre ellas la arquitectura hexagonal de Alistair Cockburn y la arquitectura cebolla (Onion Architecture) de Jeffrey Palermo (2008). Todas buscan lo mismo, separar responsabilidades, y todas lo consiguen igual: con capas y con una regla sobre hacia dónde pueden apuntar las dependencias.

El resultado que promete es un sistema independiente de los frameworks, de la interfaz de usuario, de la base de datos y de cualquier servicio externo, y que por eso se puede probar sin ninguno de ellos.

Por qué importa

Es probablemente el nombre más conocido de esta familia de estilos: el libro es lectura habitual para perfiles backend y de arquitectura, hay plantillas de proyecto «Clean Architecture» para .NET, Java, Android, Node.js o Go, y el vocabulario (entidades, casos de uso, adaptadores de interfaz, regla de dependencias) aparece en entrevistas y en revisiones de diseño. También es uno de los estilos más malinterpretados: muchos equipos copian las carpetas del diagrama sin aplicar la regla que lo sostiene, o al revés, la aplican con tanta ceremonia que el código se llena de capas que no aportan nada.

Los cuatro círculos

Del centro hacia fuera, cuanto más dentro, más abstracto y más estable; cuanto más fuera, más concreto y más cambiante:

  1. Entidades: las reglas de negocio más generales, las que seguirían siendo ciertas aunque no existiera la aplicación (un préstamo tiene un tipo de interés; un pedido cancelado no se envía). Pueden ser objetos con métodos o estructuras de datos con funciones. No cambian porque cambie la navegación de la web o la seguridad.
  2. Casos de uso: las reglas propias de esta aplicación, una por cada cosa que un usuario puede hacer («solicitar préstamo», «cancelar pedido»). Orquestan a las entidades. Cambian cuando cambia lo que la aplicación hace, no cuando cambia la base de datos.
  3. Adaptadores de interfaz: convierten los datos del formato que conviene a los casos de uso al que conviene al exterior, y al revés. Aquí viven los controladores, los presentadores y las vistas de un patrón MVC, y todo el SQL o el código de persistencia.
  4. Frameworks y drivers: el framework web, el de persistencia, la base de datos, las librerías. Normalmente se escribe poco código aquí, solo el «pegamento» con el círculo de dentro. Martin lo resume en que la web y la base de datos son detalles.

Los cuatro círculos son un esquema, no una norma: puede haber más. Lo que no cambia es la regla.

Conceptos clave

  • Regla de dependencias: las dependencias del código fuente solo apuntan hacia dentro. Nada de un círculo interior puede nombrar algo de uno exterior: ni una clase, ni una función, ni una variable. Y tampoco usar sus formatos de datos, sobre todo los que genera un framework.
  • Cruzar fronteras con inversión de dependencias: a veces el control va de dentro hacia fuera (el caso de uso tiene que mostrar un resultado o guardar algo). Para que la dependencia siga apuntando hacia dentro, el círculo interior define una interfaz y el exterior la implementa. Es la «D» de SOLID, y es el mismo mecanismo que los puertos de la arquitectura hexagonal.
  • Puertos de entrada y de salida: en la terminología del libro, el caso de uso (el interactor) implementa un input port que llama el controlador, y habla con el exterior a través de output ports: uno para el presentador y otros para la persistencia o los servicios externos.
  • Modelos de petición y de respuesta: por las fronteras solo cruzan estructuras de datos simples y aisladas (argumentos, DTO, objetos sencillos), en el formato que conviene al círculo interior. Nunca entidades hacia fuera ni filas de la base de datos hacia dentro.
  • Presentador: recibe del caso de uso los datos de la respuesta y los prepara para mostrarlos (un view model con textos ya formateados), de modo que la vista solo tenga que pintarlos.
  • Arquitectura que «grita» (Screaming Architecture, otro artículo de Martin): al abrir las carpetas del proyecto debería verse de qué va el negocio (pedidos, préstamos, envíos), no qué framework se usa (controllers, services, repositories).

En la práctica

Un caso de uso en Java siguiendo el libro al pie de la letra, con su puerto de entrada, su modelo de petición y su puerto de salida hacia el presentador. Nada de esto conoce la web ni la base de datos:

// casos de uso: puerto de entrada y modelos de petición y respuesta (datos simples)
public interface SolicitarPrestamo { void solicitar(SolicitudPrestamo peticion); }
public record SolicitudPrestamo(String clienteId, long importeCentimos, int meses) {}
public record PrestamoConcedido(String prestamoId, long cuotaCentimos) {}

// casos de uso: puertos de salida
public interface PresentadorDePrestamo { void concedido(PrestamoConcedido r); void rechazado(String motivo); }
public interface RepositorioDePrestamos { void guardar(Prestamo prestamo); }

// casos de uso: el interactor orquesta a la entidad Prestamo, que tiene las reglas generales
public final class SolicitarPrestamoInteractor implements SolicitarPrestamo {
    private final RepositorioDePrestamos prestamos;
    private final PresentadorDePrestamo presentador;
    // constructor con los dos puertos

    @Override
    public void solicitar(SolicitudPrestamo p) {
        var prestamo = Prestamo.nuevo(p.clienteId(), p.importeCentimos(), p.meses());
        if (!prestamo.esConcedible()) {
            presentador.rechazado("El importe supera el máximo para ese plazo");
            return;
        }
        prestamos.guardar(prestamo);
        presentador.concedido(new PrestamoConcedido(prestamo.id(), prestamo.cuotaMensual()));
    }
}

En el círculo de los adaptadores, el controlador traduce la petición web al modelo de petición y el presentador convierte la respuesta en lo que la vista necesita:

// adaptadores de interfaz: el presentador implementa el puerto de salida
final class PresentadorWebDePrestamo implements PresentadorDePrestamo {
    private VistaPrestamo vista;   // view model: solo textos listos para pintar

    @Override public void concedido(PrestamoConcedido r) {
        vista = new VistaPrestamo("Préstamo concedido", formatearEuros(r.cuotaCentimos()) + " al mes");
    }
    @Override public void rechazado(String motivo) { vista = new VistaPrestamo("Préstamo rechazado", motivo); }
    VistaPrestamo vista() { return vista; }
}

Fíjate en el flujo: el control va del controlador al caso de uso y de ahí al presentador, pero las dos dependencias apuntan hacia el caso de uso, porque el presentador implementa una interfaz definida dentro. Para probar el interactor basta con un repositorio y un presentador falsos que apunten lo que reciben.

Y la estructura de carpetas que «grita» el negocio en lugar del framework:

prestamos/
  dominio/          Prestamo, reglas de concesión          (entidades)
  aplicacion/       SolicitarPrestamo, SolicitarPrestamoInteractor, puertos   (casos de uso)
  adaptadores/      PrestamosController, PresentadorWebDePrestamo, RepositorioDePrestamosJdbc
  arranque/         configuración de Spring que conecta todo   (frameworks y drivers)

Muchos equipos simplifican el presentador: el caso de uso devuelve el modelo de respuesta y el controlador lo convierte. Es una variante muy extendida y válida siempre que lo devuelto sea un modelo de respuesta, no la entidad.

Caso real: Kopi Chess

Kopi Chess (código público, Java 25 y Spring Boot 4) describe su propio código como «anillos, como una cebolla», y sus módulos Maven encajan casi uno a uno con los círculos: kopi-domain (entidades: las reglas del ajedrez), kopi-application (casos de uso y puertos), los kopi-adapter-* (adaptadores de interfaz: web, REST, PostgreSQL, Stockfish) y kopi-bootstrap (el framework que lo conecta todo). Usa la variante simplificada: cada caso de uso devuelve un modelo de respuesta (GameView) en lugar de llamar a un presentador. La regla de dependencias la comprueban el compilador y ArchUnit. Explicado paso a paso en Aprendizajes de Kopi Chess.

Errores frecuentes

  • Copiar las carpetas y olvidar la regla: tener domain, application e infrastructure no sirve de nada si el dominio importa clases del framework. Comprueba la regla con módulos separados o con pruebas de arquitectura (ArchUnit en Java).
  • Confundir entidades con entidades de JPA: las entidades de la arquitectura limpia son objetos de negocio, no clases con @Entity mapeadas a tablas. Mezclarlas ata el centro a la base de datos.
  • Pasar entidades o filas por las fronteras: devolver la entidad al controlador o subir una fila de la base de datos al caso de uso rompe la regla por los datos aunque no la rompa por los import.
  • Ceremonia por defecto: un puerto, un interactor, un presentador, un modelo de petición, otro de respuesta y tres mapeos para guardar un formulario. En partes sin lógica de negocio, cuesta más de lo que aporta.
  • Entidades vacías y casos de uso que lo hacen todo: si las entidades son solo datos y toda la lógica está en los casos de uso, las reglas generales se repiten entre casos de uso.
  • Tomar los cuatro círculos como dogma: son un esquema. Lo obligatorio es que las dependencias apunten hacia dentro.

Limpia, hexagonal y cebolla

HexagonalCebollaLimpia
Autor y añoAlistair Cockburn, 2005Jeffrey Palermo, 2008Robert C. Martin, 2012
ImagenUn núcleo con puertos y adaptadores alrededor.Capas concéntricas con el modelo de dominio en el centro.Cuatro círculos: entidades, casos de uso, adaptadores, frameworks.
Qué subrayaLa simetría: interfaz, base de datos y pruebas son por igual «el exterior».Todo el acoplamiento va hacia el centro.La regla de dependencias, también para los datos, y cómo cruzar cada frontera.
Por dentro del núcleoNo lo detalla.Dominio, servicios de dominio y de aplicación.Separa reglas generales (entidades) y propias de la aplicación (casos de uso).

Las tres comparten lo esencial y en la práctica se mezclan. Frente a la arquitectura en capas clásica, la diferencia es la misma: allí el negocio depende de la capa de datos; aquí la capa de datos depende del negocio.

Cuándo elegirla: aplicaciones con reglas de negocio que duran más que las tecnologías que las rodean, varias entradas (web, API, mensajes) sobre los mismos casos de uso o necesidad de probar el negocio sin infraestructura. Cuándo no: un CRUD sencillo, un prototipo o un servicio muy pequeño, donde unas capas bien separadas bastan.
