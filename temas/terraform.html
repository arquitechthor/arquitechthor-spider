Qué es

Terraform es una herramienta de infraestructura como código creada por HashiCorp en 2014. Describes en ficheros de texto lo que quieres tener en la nube (redes, máquinas virtuales, bases de datos, buckets de almacenamiento, permisos, registros DNS…) y Terraform se encarga de crearlo, cambiarlo o borrarlo hasta que la realidad coincida con lo escrito.

Los ficheros se escriben en HCL, un lenguaje declarativo: dices qué debe existir, no los pasos para conseguirlo. Terraform compara eso con lo que ya existe, calcula un plan con las diferencias y, cuando lo apruebas, lo aplica llamando a la API de cada proveedor. Funciona con AWS, Azure, Google Cloud y cientos de servicios más (GitHub, Cloudflare, Datadog, Kubernetes…) gracias a sus providers. Esta ficha describe Terraform 1.x (la 1.17 es de octubre de 2026).

Por qué importa

Es la herramienta de infraestructura como código más extendida y la única gran opción que no está atada a una nube: el mismo flujo de trabajo sirve para AWS, Azure o un proveedor de DNS. Aparece en buena parte de las ofertas de DevOps, plataforma y cloud, y tiene certificación propia (HashiCorp Terraform Associate), que este sitio cubrirá más adelante.

Sobre todo, cambia cómo se trabaja: la infraestructura pasa por Git, se revisa en una petición de cambios como el código, se puede reproducir en otro entorno o región y el plan te dice antes de tocar nada qué se va a crear, modificar o destruir.

Conceptos clave

  • Provider: el complemento que sabe hablar con una plataforma (hashicorp/aws, hashicorp/azurerm…). Se descargan del Terraform Registry y se fija su versión en required_providers.
  • Resource: un bloque resource "tipo" "nombre" por cada cosa que Terraform gestiona: un bucket, una instancia, una regla de firewall. Su dirección (aws_s3_bucket.fotos) es como Terraform lo identifica.
  • Data source: un bloque data que lee algo que ya existe y no gestiona Terraform (la imagen de sistema más reciente, una red creada por otro equipo) para usarlo en tus recursos.
  • Variables, locals y outputs: las variables son los parámetros de entrada (región, tamaño), los locals son valores calculados para no repetirse y los outputs exponen resultados (una URL, un identificador) a quien use la configuración.
  • Estado (state): el fichero terraform.tfstate donde Terraform apunta qué recurso real corresponde a cada bloque y sus atributos. Sin él no sabría qué creó. En equipo se guarda en un backend remoto (un bucket de S3, Azure Storage, Google Cloud Storage o HCP Terraform) con bloqueo, para que dos personas no lo modifiquen a la vez.
  • Plan y apply: plan compara configuración, estado y realidad y muestra los cambios (+ crear, ~ modificar en el sitio, -/+ destruir y volver a crear, - destruir). apply los ejecuta.
  • Grafo de dependencias: si un recurso usa un atributo de otro (aws_s3_bucket.fotos.id), Terraform deduce el orden y crea en paralelo lo que no depende entre sí. depends_on solo hace falta para dependencias que no se ven en el código.
  • Módulos: una carpeta de ficheros .tf que se reutiliza con un bloque module y sus variables, como una función. Hay módulos públicos en el Registry para redes, clústeres de Kubernetes, etc.
  • count y for_each: crean varias copias de un recurso. for_each las identifica por clave (["fotos"], ["videos"]) y count por posición ([0], [1]).
  • Deriva (drift): diferencias entre el estado y la realidad porque alguien cambió algo a mano en la consola. El siguiente plan intentará deshacerlas.

En la práctica

1. Configuración. Un bucket de S3 con versionado. El bloque terraform fija la versión del provider y guarda el estado en otro bucket, con bloqueo nativo (use_lockfile):

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  backend "s3" {
    bucket       = "mi-empresa-tfstate"
    key          = "fotos/prod.tfstate"
    region       = "eu-west-1"
    use_lockfile = true
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  type    = string
  default = "eu-west-1"
}

resource "aws_s3_bucket" "fotos" {
  bucket = "mi-empresa-fotos-prod"
}

resource "aws_s3_bucket_versioning" "fotos" {
  bucket = aws_s3_bucket.fotos.id   # referencia: crea antes el bucket
  versioning_configuration {
    status = "Enabled"
  }
}

output "bucket_arn" {
  value = aws_s3_bucket.fotos.arn
}

2. Flujo de trabajo. Los mismos comandos en local y en un pipeline de CI/CD:

terraform init                   # descarga providers y conecta con el backend
terraform fmt                    # formato estándar
terraform validate               # sintaxis y tipos, sin llamar a la nube
terraform plan -out=cambios.tfplan
terraform apply cambios.tfplan   # aplica exactamente el plan revisado

init crea también .terraform.lock.hcl, que anota la versión exacta de cada provider: se sube al repositorio para que todo el equipo y el pipeline usen las mismas. La carpeta .terraform/ y los ficheros de estado, en cambio, no se suben nunca.

Errores frecuentes

  • Estado local o en Git: en un portátil se pierde y en el repositorio se pisa entre compañeros. Usa un backend remoto con bloqueo desde el primer día (en S3, use_lockfile; el bloqueo con una tabla de DynamoDB está obsoleto).
  • Creer que sensitive protege los secretos: solo los oculta en la salida de la consola. Las contraseñas y claves que pasan por Terraform quedan en texto plano en el estado y en el plan, así que el backend debe estar cifrado y con acceso restringido. Mejor aún: valores ephemeral y argumentos de solo escritura (*_wo), que no se guardan, o que el secreto lo genere y guarde un gestor de secretos.
  • Cambios a mano en la consola: crean deriva y el siguiente apply los revierte. Si hubo que tocar algo con urgencia, llévalo después al código o revísalo con terraform plan -refresh-only.
  • Renombrar un recurso sin más: para Terraform es borrar uno y crear otro (con sus datos dentro). Usa un bloque moved para cambiar la dirección sin destruir nada, e import para adoptar recursos que ya existían.
  • count sobre una lista que cambia: si quitas el primer elemento, todos los demás se desplazan de índice y se recrean. Con for_each y claves estables solo se toca el que quitaste.
  • Un único estado gigante: cada plan tarda más y un error puede afectar a todo. Divide por sistema y entorno, con un estado y unas credenciales propios para producción. Los workspaces de la CLI comparten backend: HashiCorp no los recomienda para aislar entornos, sino para copias temporales.
  • No leer el plan: un -/+ en una base de datos significa destruirla. Revisa el plan en la petición de cambios y protege lo crítico con lifecycle { prevent_destroy = true }.

Terraform, OpenTofu y las herramientas de cada nube

En 2023 HashiCorp cambió la licencia de Terraform de MPL 2.0 (código abierto) a BSL, que limita usarlo para crear productos competidores. Como respuesta nació OpenTofu, una bifurcación de la última versión abierta gestionada bajo la Linux Foundation. HashiCorp pasó a formar parte de IBM en 2025.

NubesCualquiera con provider.Igual: usa los mismos providers.Solo la suya.

CuándoVarias nubes o servicios, o el estándar de tu empresa.Quieres una licencia abierta con la misma forma de trabajar.Trabajas solo en una nube y prefieres su herramienta nativa.

Para quien prefiere un lenguaje de programación en lugar de HCL existen el AWS CDK (genera CloudFormation) y Pulumi.
