Qué es

Apache Kafka es una plataforma de transmisión de eventos: un registro distribuido, duradero y ordenado donde unas aplicaciones escriben eventos («se ha creado el pedido 42», «ha cambiado el precio de este producto») y otras los leen, cada una a su ritmo, ahora o días después. Nació en LinkedIn en 2011, es un proyecto de la Apache Software Foundation y la línea actual es la 4.x.

A diferencia de una cola clásica, Kafka no borra un mensaje cuando alguien lo lee: lo guarda durante el tiempo configurado, y cada consumidor lleva la cuenta de por dónde va. Eso permite que muchos sistemas lean los mismos eventos y que uno nuevo los relea desde el principio.

Vocabulario para empezar

  • Evento: un hecho que ya ha ocurrido, con una clave, un valor (normalmente JSON o Avro) y una marca de tiempo.
  • Productor y consumidor: la aplicación que escribe eventos y la que los lee.
  • Broker: cada servidor de Kafka. Un clúster tiene varios para repartir carga y no perder datos si uno cae.

Por qué importa

Es la pieza central de la arquitectura orientada a eventos: en lugar de que el servicio de pedidos llame uno a uno a facturación, almacén y notificaciones, publica «pedido creado» y cada uno reacciona. Los servicios quedan desacoplados (el productor no sabe quién lee), el sistema aguanta picos (los eventos esperan en Kafka) y se puede reconstruir el estado o alimentar análisis releyendo el historial. Lo usan la mayoría de grandes empresas, a menudo gestionado (Confluent Cloud, Amazon MSK).

Conceptos clave

  • Topic: una categoría de eventos con nombre (pedidos, precios).
  • Partición: cada topic se divide en particiones, que son registros ordenados donde solo se añade al final. Kafka garantiza el orden dentro de una partición, no en todo el topic. Las particiones permiten repartir la carga entre brokers y consumidores.
  • Clave y orden: los eventos con la misma clave van a la misma partición. Si la clave es el id del pedido, todos los eventos de un pedido se leen en orden.
  • Offset: la posición de cada evento en su partición. El consumidor guarda (commit) el último offset procesado para continuar desde ahí tras reiniciarse.
  • Grupo de consumidores: varias instancias de la misma aplicación con el mismo group.id se reparten las particiones: cada partición la lee una sola instancia del grupo. Por eso no tiene sentido tener más instancias que particiones. Grupos distintos leen todos los eventos, cada uno por su cuenta.
  • Retención y compactación: los eventos se borran por tiempo o tamaño; en un topic compactado se conserva solo el último valor de cada clave (útil para el estado actual de algo).
  • Replicación: cada partición tiene copias en varios brokers. Con acks=all, el productor espera a que las réplicas sincronizadas confirmen la escritura, y no se pierde el evento si cae un broker.
  • Garantías de entrega: por defecto, al menos una vez: un evento puede llegar repetido (por ejemplo, si el consumidor procesa y muere antes de guardar el offset). Por eso los consumidores deben ser idempotentes. Kafka ofrece productores idempotentes y transacciones para «exactamente una vez» dentro de Kafka.
  • KRaft: desde Kafka 4.0, el clúster se coordina solo, sin ZooKeeper, que era un sistema aparte obligatorio en versiones anteriores.
  • Schema Registry: un servicio que guarda los esquemas de los eventos (Avro, JSON Schema, Protobuf) y evita que un productor publique un formato que rompa a los consumidores.

En la práctica

Productor y consumidor con el cliente oficial de Java, usando el id del producto como clave para mantener el orden por producto:

// Productor
var props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("acks", "all");
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());
try (var productor = new KafkaProducer<String, String>(props)) {
    productor.send(new ProducerRecord<>("precios", "producto-123", "{\"precio\": 29.99}"));
}

// Consumidor
props.put("group.id", "servicio-catalogo");
props.put("enable.auto.commit", "false");
try (var consumidor = new KafkaConsumer<String, String>(props)) {
    consumidor.subscribe(List.of("precios"));
    while (true) {
        for (var registro : consumidor.poll(Duration.ofSeconds(1))) {
            actualizarPrecio(registro.key(), registro.value());   // idempotente
        }
        consumidor.commitSync();                                  // después de procesar
    }
}

En la práctica se usa a través del framework: Spring for Apache Kafka (@KafkaListener) o SmallRye Reactive Messaging en Quarkus (@Incoming, @Outgoing).

Kafka encaja cuando hay mucho volumen, varios consumidores del mismo flujo, necesidad de orden por clave o de releer. Para repartir tareas entre trabajadores sin más, una cola es más sencilla.

Errores frecuentes

  • Esperar orden global: solo hay orden por partición. Elige bien la clave.
  • Consumidores no idempotentes: los duplicados ocurren. Procesar dos veces el mismo evento no debería cambiar el resultado.
  • Guardar el offset antes de procesar: si el proceso muere a mitad, el evento se pierde. Guárdalo después.
  • Pocas particiones: limitan cuántas instancias pueden consumir en paralelo, y aumentarlas después cambia a qué partición va cada clave.
  • Mensajes venenosos: un evento que siempre falla bloquea su partición. Prevé reintentos limitados y un topic de mensajes fallidos (dead letter).
  • Escribir en la base de datos y en Kafka sin coordinar: si una de las dos falla, quedan desincronizadas. El patrón outbox lo resuelve.
