Qué es

Git es un sistema de control de versiones distribuido: guarda la historia completa de un proyecto como una serie de fotos (commits), permite trabajar en paralelo en ramas y combinarlas después. «Distribuido» significa que cada copia del repositorio tiene toda la historia: se puede trabajar sin conexión y no hay un único servidor imprescindible.

Lo creó Linus Torvalds en 2005 para el núcleo de Linux y hoy es el estándar casi universal. GitHub, GitLab y Bitbucket son servicios que alojan repositorios Git y añaden revisión de código (pull requests), integración continua y permisos.

Vocabulario para empezar

  • Repositorio: la carpeta del proyecto más su historia (guardada en la carpeta oculta .git).
  • Remoto: otra copia del repositorio, normalmente en un servidor, con un nombre (por convención origin).
  • Área de preparación (staging): la zona intermedia donde eliges qué cambios entran en el siguiente commit (git add).
  • PR (pull request): la propuesta, en GitHub o similar, de fusionar una rama en otra, con revisión y comprobaciones automáticas antes de aceptarla.

Por qué importa

Todo el trabajo en equipo pasa por Git: cada cambio que haces, cada revisión, cada despliegue que sale de una rama. Saber usarlo más allá de add, commit y push marca la diferencia cuando algo se tuerce: un conflicto al fusionar, una rama que va 40 commits por detrás, un commit que hay que deshacer en una rama compartida o un despliegue que no tiene lo que creías.

El modelo mental

  • Commit: una foto completa del proyecto, con autor, fecha, mensaje y un enlace a su commit padre (o a dos, si es una fusión). Se identifica por un hash, una huella de 40 caracteres calculada a partir de su contenido.
  • Rama: solo una etiqueta móvil que apunta a un commit. Crear una rama es instantáneo.
  • HEAD: dónde estás ahora: normalmente, la rama en la que trabajas.
  • Ramas remotas: origin/main es tu copia local de cómo estaba main en el servidor la última vez que preguntaste. git fetch la actualiza sin tocar tu trabajo; git pull hace fetch y además fusiona.

Combinar ramas: merge y rebase

  • Merge con avance rápido: si tu rama no ha cambiado desde que salió la otra, Git solo mueve la etiqueta hacia delante. No hay commit nuevo.
  • Merge con commit de fusión: si las dos ramas avanzaron, Git crea un commit con dos padres que junta ambas. La historia conserva cómo pasó todo.
  • Rebase: reescribe tus commits como si hubieran salido del punto más reciente de la otra rama. La historia queda lineal, pero los commits son nuevos (otro hash). No hagas rebase de commits que otros ya tienen: obligarías a todos a arreglar su copia.
  • Conflicto: cuando las dos ramas cambiaron las mismas líneas, Git no decide y marca el fichero con las dos versiones entre <<<<<<<, ======= y >>>>>>>. Resolverlo es escribir el resultado correcto, que a menudo no es «el mío», ni «el suyo», ni «los dos pegados».

En la práctica

Poner al día una rama de trabajo con la rama principal, comprobando antes si habrá conflictos:

git fetch origin
git rev-list --left-right --count origin/main...mi-rama    # cuántos commits por detrás / por delante
git merge-tree --write-tree --name-only origin/main mi-rama  # simula la fusión sin tocar nada
git switch mi-rama
git merge origin/main                                       # o: git rebase origin/main, si nadie más la usa
# ...resolver conflictos, git add, y ejecutar las pruebas antes de hacer commit
git push

Deshacer sin miedo:

git restore fichero.txt          # descarta cambios sin guardar de un fichero
git revert a1b2c3d               # crea un commit que deshace otro (seguro en ramas compartidas)
git reset --soft HEAD~1          # deshace el último commit local, conservando los cambios
git reflog                       # dónde ha estado HEAD: rescata commits "perdidos"

Buenos mensajes de commit: muchos equipos siguen Conventional Commits (feat:, fix:, docs:…) o empiezan por el código del ticket. Un mensaje dice qué cambia y por qué; el cómo ya está en el código.

Commits firmados: con una clave GPG o SSH, el servidor puede verificar que el commit lo hizo quien dice. Algunos repositorios rechazan los que no van firmados.

Caso real: Kopi Chess

En Kopi Chess cada cambio llega a main por una pull request desde una rama con prefijo (feat/, docs/…), y se fusiona con commit de fusión, así que la historia muestra cada PR como una unidad. Los mensajes siguen Conventional Commits con ámbito opcional (feat(web): …, ci: …), y eso permite generar el CHANGELOG.md de cada versión automáticamente con git-cliff a partir de la historia. Las versiones se marcan con etiquetas (v1.1.0).

Errores frecuentes

  • Resolver un conflicto quitando solo las marcas: dejar las dos versiones pegadas puede producir un fichero válido para Git pero roto para el programa. En YAML, por ejemplo, una clave puede quedarse sin su contenido y valer nulo. Lee el resultado y ejecuta las pruebas antes de hacer commit.
  • Trabajar con una rama muy desfasada: cuanto más tardas en traer los cambios de la principal, peores son los conflictos. Actualiza a menudo.
  • git push --force en una rama compartida: borras el trabajo de otros. Si de verdad hace falta, usa --force-with-lease, que falla si alguien subió algo nuevo.
  • Commits gigantes con mensajes vagos: «cambios» no ayuda a revisar ni a encontrar un error después. Commits pequeños y con sentido.
  • Subir secretos: una clave en un commit queda en la historia aunque la borres después. Rótala y usa un .gitignore y un gestor de secretos.
  • Confundir la rama base de una PR: una PR contra la rama equivocada arrastra commits que no son tuyos. Revisa la base antes de pedir revisión.
