Qué es

Quarkus es un framework de Java para escribir servicios de servidor (APIs REST, consumidores de mensajes, tareas programadas) pensado desde el principio para contenedores y Kubernetes: arranca en muy poco tiempo y consume poca memoria. Lo creó Red Hat en 2019, es software libre y la línea actual es la 3.x.

Ocupa el mismo hueco que Spring Boot: inyección de dependencias, configuración, servidor web, acceso a datos, pruebas… La diferencia está en cuándo hace el trabajo pesado: Quarkus lo hace casi todo al compilar, no al arrancar.

Vocabulario para empezar

  • Framework: conjunto de piezas ya hechas (servidor web, configuración, conexión a bases de datos) sobre las que escribes solo la lógica de tu aplicación.
  • Inyección de dependencias: en lugar de que cada clase cree los objetos que necesita, el framework se los entrega ya construidos. Cada objeto gestionado así se llama bean.
  • Extensión: en Quarkus, cada integración (REST, Kafka, PostgreSQL, un cliente de LLM) es una extensión que se añade como dependencia y que trae su configuración y su parte de compilación.
  • Imagen nativa: un ejecutable del sistema operativo generado con GraalVM a partir del código Java, que no necesita una JVM para arrancar.

Por qué importa

En un clúster con decenas de microservicios, cada uno con varias réplicas, el tiempo de arranque y la memoria se pagan muchas veces: en la factura, al escalar cuando sube la carga y al desplegar. Quarkus se diseñó para eso. Además, su modo de desarrollo (recarga en caliente al guardar un fichero) y los Dev Services (arranca solo una base de datos o un Kafka de prueba en Docker si no configuras uno) hacen que el ciclo de cambiar y probar sea muy corto.

Es habitual encontrarlo en empresas que conviven con Spring: muchos de sus conceptos (CDI, JAX-RS, MicroProfile Config) son estándares de Jakarta EE y MicroProfile, así que quien viene de Java empresarial los reconoce.

Cómo funciona: el trabajo se hace al compilar

Un framework clásico, al arrancar, escanea el classpath (todas las clases disponibles), lee anotaciones con reflexión, decide qué beans crear y monta proxies. Quarkus mueve casi todo eso a la compilación:

  1. Al compilar, cada extensión analiza tu código y genera el código que conecta las piezas (qué beans hay, qué rutas REST, qué clientes).
  2. El resultado es una aplicación que, al arrancar, solo tiene que ejecutar ese código ya preparado.
  3. Opcionalmente, GraalVM la convierte en una imagen nativa: arranca en milisegundos y usa una fracción de la memoria, a cambio de una compilación mucho más lenta y de limitaciones con la reflexión.

Una consecuencia práctica: parte de la configuración se fija al compilar. Si cambias una propiedad de tiempo de compilación en el entorno de producción, no tiene efecto; hay que volver a construir. La documentación marca cada propiedad con un candado cuando es de este tipo.

Conceptos clave

  • CDI con ArC: Quarkus implementa el estándar CDI con su propio motor (ArC), resuelto al compilar. Los beans se declaran con @ApplicationScoped (una instancia para toda la aplicación) o @RequestScoped, y se inyectan por constructor o con @Inject.
  • Configuración: se lee de application.properties (o application.yaml con la extensión quarkus-config-yaml), de variables de entorno y de propiedades del sistema, con este orden de prioridad de mayor a menor: sistema, entorno, fichero. Se inyecta con @ConfigProperty o se agrupa en interfaces con @ConfigMapping.
  • Perfiles: una propiedad puede tener un valor distinto por entorno con el prefijo %perfil. (en YAML, una clave "%perfil"). Vienen tres de serie: dev (modo desarrollo), test (pruebas) y prod (por defecto al ejecutar el paquete). Se pueden crear otros (por ejemplo, uno por entorno) y activarlos con QUARKUS_PROFILE.
  • Quarkus REST: el servidor REST (antes llamado RESTEasy Reactive), con las anotaciones de JAX-RS: @Path, @GET, @QueryParam…
  • REST Client: un cliente HTTP declarativo: escribes una interfaz anotada y Quarkus genera la implementación. Se registra con @RegisterRestClient(configKey = "…") y su URL, tiempos de espera y filtros se configuran bajo quarkus.rest-client."clave".*.
  • Pruebas: @QuarkusTest arranca la aplicación una vez para todas las pruebas de ese tipo; @InjectMock sustituye un bean por un mock de Mockito solo en esa clase de prueba.

En la práctica

Un recurso REST que delega en un servicio, y el servicio que llama a otra API con un REST Client:

@Path("/api/v1/categorias")
@Produces(MediaType.APPLICATION_JSON)
public class CategoriaResource {

    private final CategoriaService servicio;

    CategoriaResource(CategoriaService servicio) {
        this.servicio = servicio;
    }

    @GET
    public List<Categoria> listar(@QueryParam("limit") @DefaultValue("100") int limit) {
        return servicio.listar(limit);
    }
}

@RegisterRestClient(configKey = "catalogo-externo")
public interface CatalogoClient {
    @GET
    @Path("/categories")
    List<Categoria> categorias(@QueryParam("size") int size);
}

Y su configuración, con un valor por defecto y otro solo para producción:

quarkus:
  rest-client:
    catalogo-externo:
      url: ${CATALOGO_URL:http://localhost:8089}
      read-timeout: 10000
"%prod":
  quarkus:
    log:
      level: WARN

El día a día se hace con quarkus dev (o ./mvnw quarkus:dev, ./gradlew quarkusDev): la aplicación se recarga al guardar, y la página /q/dev-ui enseña los beans, la configuración y las extensiones.

EcosistemaGrande, centrado en la nubeEl más grande de Java

Los dos sirven para lo mismo. Quarkus brilla cuando el arranque y la memoria cuentan (muchas réplicas, escalado rápido, funciones serverless); Spring gana en número de bibliotecas, ejemplos y gente que lo conoce.

Errores frecuentes

  • Esperar que una propiedad de compilación cambie en tiempo de ejecución: no lo hará. Revisa si lleva el candado en la documentación y reconstruye.
  • Inyectar en campos privados: funciona, pero obliga a Quarkus a usar reflexión. Prefiere constructor o campos con visibilidad de paquete.
  • Romper el YAML al fusionar ramas: en application.yaml, una clave sin contenido ("modelo": sin nada debajo) vale nulo y la extensión que la necesitaba no arranca. Tras resolver un conflicto, ejecuta las pruebas: un @QuarkusTest falla en cuanto falta una propiedad obligatoria.
  • Olvidar el perfil activo: si creas perfiles propios por entorno, el paquete arranca con prod salvo que el despliegue fije QUARKUS_PROFILE.
  • Reflexión sin registrar en imagen nativa: lo que se carga por reflexión (algunas bibliotecas de JSON, por ejemplo) hay que declararlo con @RegisterForReflection.
  • Pruebas lentas por cambiar de perfil: cada @TestProfile distinto obliga a reiniciar la aplicación de pruebas. Agrupa las pruebas que comparten configuración.
