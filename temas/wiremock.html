Qué es

WireMock es un servidor HTTP falso para pruebas: arranca en un puerto local y responde a las peticiones como tú le digas («a GET /categories?page=0 responde 200 con este JSON», «a la tercera petición, tarda 5 segundos»). Tu código cree que habla con la API real, pero habla con WireMock.

Es software libre, está escrito en Java y la línea actual es la 3.x (con el grupo de Maven org.wiremock). También funciona como programa independiente o en un contenedor, para usarlo desde cualquier lenguaje.

Vocabulario para empezar

  • Stub: una respuesta preparada para una petición concreta. En WireMock, una regla «si llega esto, responde esto».
  • Doble de prueba: cualquier sustituto falso de una dependencia. Un mock de Mockito sustituye un objeto Java; WireMock sustituye un servidor entero.
  • Prueba de integración: la que prueba tu código junto con piezas reales: aquí, el cliente HTTP de verdad, la serialización JSON y la gestión de errores.

Por qué importa

Casi todos los servicios llaman a otras APIs: la de un proveedor, la de un cliente, la de otro equipo. Probar ese código contra la API real es lento, frágil (depende de la red, de las credenciales y de los datos de ese día) y a veces imposible (no puedes pedirle a un tercero que te devuelva un 503 cuando quieras). Sustituir el cliente por un mock de Mockito es rápido, pero no prueba lo que más falla: la URL, los parámetros, las cabeceras, la conversión del JSON y qué pasa con un error o un tiempo de espera. WireMock prueba todo eso sin depender del tercero.

Conceptos clave

  • Coincidencia de peticiones: un stub se aplica según método, URL o ruta (exacta o por expresión regular), parámetros de consulta, cabeceras y cuerpo (incluido JSON parcial o JSONPath).
  • Respuestas: estado, cabeceras y cuerpo (en línea o desde un fichero en __files), con plantillas para reutilizar datos de la petición.
  • Fallos simulados: retrasos fijos o aleatorios (withFixedDelay), conexiones cortadas, respuestas vacías o basura. Es la forma de probar tiempos de espera y errores de red.
  • Verificación: comprobar después qué peticiones llegaron (verify(getRequestedFor(...))), por ejemplo que se envió la cabecera de autenticación o que no se llamó a la API cuando no tocaba.
  • Escenarios: respuestas con estado: la primera petición falla y la segunda va bien, para probar reintentos.
  • Grabar y reproducir: WireMock puede hacer de proxy contra la API real y guardar sus respuestas como stubs. Útil para empezar; luego conviene limpiar los datos.

En la práctica

Con JUnit 5, la anotación @WireMockTest arranca un servidor por clase en un puerto libre y lo inyecta en la prueba:

@WireMockTest
class CatalogoClientTest {

    @Test
    void devuelveLasCategoriasDeLaPrimeraPagina(WireMockRuntimeInfo wm) {
        stubFor(get(urlPathEqualTo("/categories"))
                .withQueryParam("page", equalTo("0"))
                .withHeader("Authorization", matching("Basic .+"))
                .willReturn(okJson("""
                        {"totalElements": 2, "data": [{"id": 1}, {"id": 2}]}
                        """)));

        var cliente = new CatalogoClient(wm.getHttpBaseUrl(), credenciales);

        assertThat(cliente.categorias(0).data()).hasSize(2);
    }

    @Test
    void convierteUnTiempoDeEsperaEnUnErrorControlado(WireMockRuntimeInfo wm) {
        stubFor(get(anyUrl()).willReturn(ok().withFixedDelay(3_000)));

        var cliente = new CatalogoClient(wm.getHttpBaseUrl(), credenciales, Duration.ofSeconds(1));

        assertThatThrownBy(() -> cliente.categorias(0)).isInstanceOf(ProveedorNoDisponible.class);
    }
}

En una aplicación de Spring Boot o Quarkus, la idea es la misma: se apunta la URL del cliente (una propiedad de configuración) a la de WireMock y se prueba de punta a punta, desde el endpoint propio hasta la respuesta simulada del tercero.

Caso real: Kopi Chess

Kopi Chess resuelve lo mismo sin WireMock: su adaptador que habla con el inicio de sesión y la API de Kopi se prueba contra FakeKopi, un servidor falso escrito con el HttpServer que trae el propio JDK.

  • Arranca en 127.0.0.1 con puerto 0, es decir, en un puerto libre que se pregunta después, igual que WireMock.
  • Cada prueba declara qué responde cada ruta (on("GET", "/chess/games", ...)), que es la idea de un stub.
  • Guarda todas las peticiones recibidas para comprobar luego qué se envió, que es la verificación de WireMock.

Para un adaptador pequeño y unas pocas rutas, un servidor propio basta y no añade dependencias. Cuando hacen falta coincidencias complejas, fallos de red simulados o escenarios con estado, WireMock ahorra mucho código.

WireMock, Mockito o pruebas de contrato

  • Mockito: sustituye una interfaz Java. Ideal para probar la lógica que usa el cliente; no prueba el cliente.
  • WireMock: sustituye el servidor. Prueba el cliente HTTP de verdad y sus errores.
  • Pruebas de contrato (Pact, Spring Cloud Contract): además comprueban que el proveedor real cumple lo que el stub supone. Útiles entre equipos de la misma empresa; con un tercero que no participa, WireMock con respuestas copiadas de la documentación es lo práctico.

Errores frecuentes

  • Stubs que no se parecen a la API real: si inventas el JSON, la prueba pasa y producción falla. Copia respuestas reales (sin datos sensibles) a ficheros de prueba.
  • Coincidencias demasiado laxas: un anyUrl() en todo hace que la prueba pase aunque envíes los parámetros mal. Comprueba ruta, parámetros y cabeceras importantes.
  • Puerto fijo: choca en la integración continua. Usa el puerto dinámico que te da WireMock.
  • Probar solo el caso feliz: la razón de ser de WireMock es simular el 500, el 403 y el tiempo de espera. Escribe esas pruebas.
  • Confundirlo con una prueba de la API real: WireMock comprueba tu lado. Si el tercero cambia su contrato, te enterarás en producción; vigila sus avisos de versiones.
