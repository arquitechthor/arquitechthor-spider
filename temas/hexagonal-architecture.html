Qué es

La arquitectura hexagonal, también llamada de puertos y adaptadores (Ports and Adapters), es una forma de organizar una aplicación para que su lógica de negocio no dependa de cómo se comunica con el mundo exterior. La propuso Alistair Cockburn en un artículo de 2005.

La idea es separar un dentro y un fuera. Dentro está lo que la aplicación sabe hacer: sus reglas y sus casos de uso. Fuera está todo lo demás: la interfaz web, una API REST, la base de datos, una cola de mensajes, un servicio de terceros, las pruebas automáticas. El dentro define unas interfaces, los puertos, y cada tecnología concreta se conecta a ellos mediante un adaptador. Así, la misma lógica puede usarse desde una web, desde un script o desde una prueba, y guardar sus datos en PostgreSQL o en memoria, sin cambiar una línea del núcleo.

El hexágono no tiene nada de especial: Cockburn lo dibujó así para dejar sitio a varios puertos alrededor y romper con el dibujo clásico de capas apiladas, en el que parece que solo hay un «arriba» (la interfaz) y un «abajo» (la base de datos).

Por qué importa

En muchos proyectos la lógica de negocio acaba repartida entre controladores, consultas SQL y anotaciones del framework. Probarla exige arrancar la aplicación entera con su base de datos, y cambiar de tecnología obliga a tocarla. La arquitectura hexagonal ataca justo eso:

  • Pruebas rápidas: el núcleo se prueba con objetos en memoria, en milisegundos, sin servidor ni base de datos.
  • Tecnología reemplazable: cambiar de base de datos, de proveedor de correo o de interfaz es escribir otro adaptador.
  • Desarrollo en paralelo: se puede construir y demostrar la lógica antes de decidir la base de datos o con servicios externos que aún no existen.
  • Código que cuenta el negocio: el núcleo habla de pedidos, partidas o facturas, no de tablas ni de peticiones HTTP.

Es uno de los estilos más citados en el desarrollo backend actual, sobre todo junto a DDD y en microservicios, y una pregunta habitual en entrevistas de perfiles senior.

Conceptos clave

  • Núcleo (aplicación): el código de negocio. Suele dividirse en el dominio (las entidades y reglas: un pedido, sus líneas, cuándo se puede cancelar) y los casos de uso (una clase o función por cada cosa que un usuario puede hacer: «crear pedido», «cancelar pedido»).
  • Puerto: una interfaz que define una conversación del núcleo con el exterior, con el vocabulario del negocio. Cockburn los agrupa por propósito: «para hacer pedidos», «para guardar pedidos», «para notificar al cliente».
  • Puerto de entrada (primario, driving): cómo se usa la aplicación. Suele ser la interfaz de un caso de uso (CrearPedido). Lo llaman los adaptadores de entrada.
  • Puerto de salida (secundario, driven): lo que la aplicación necesita del exterior (RepositorioDePedidos, Notificador). Lo define el núcleo y lo implementan los adaptadores de salida.
  • Adaptador: el código que traduce entre un puerto y una tecnología. De entrada: un controlador web, un consumidor de mensajes, una línea de comandos, una prueba. De salida: un repositorio con JDBC o JPA, un cliente HTTP, un envío de correo. Un puerto puede tener varios adaptadores (el real y uno en memoria para las pruebas).
  • Regla de dependencias: las dependencias del código fuente solo apuntan hacia dentro. Los adaptadores conocen al núcleo; el núcleo no conoce a ningún adaptador ni al framework.
  • Inversión de dependencias: es lo que hace posible la regla. Cuando un caso de uso necesita guardar, no llama a la base de datos: llama a una interfaz suya, y el adaptador de fuera la implementa. Es la «D» de SOLID.
  • Raíz de composición (composition root): el único sitio, en el arranque, que conoce todas las piezas y conecta cada puerto con su adaptador, a mano o con un contenedor de inyección de dependencias.

En la práctica

Un ejemplo mínimo en Java, de dentro hacia fuera. Primero, el núcleo: un puerto de salida y un caso de uso que lo recibe por el constructor. Ninguna de las dos clases importa nada de Spring ni de JDBC.

// núcleo: puerto de salida, con lenguaje del negocio
public interface RepositorioDePedidos {
    Optional<Pedido> buscar(PedidoId id);
    void guardar(Pedido pedido);
}

// núcleo: caso de uso (su interfaz CancelarPedido es el puerto de entrada)
public final class CancelarPedidoServicio implements CancelarPedido {
    private final RepositorioDePedidos pedidos;

    public CancelarPedidoServicio(RepositorioDePedidos pedidos) {
        this.pedidos = pedidos;
    }

    @Override
    public void cancelar(PedidoId id) {
        var pedido = pedidos.buscar(id).orElseThrow(() -> new PedidoNoEncontrado(id));
        pedidos.guardar(pedido.cancelar());   // la regla "¿se puede cancelar?" vive en Pedido
    }
}

Fuera, los adaptadores. Uno de salida, con la tecnología real, y otro de entrada, que traduce HTTP al caso de uso:

// adaptador de salida: implementa el puerto con JDBC
public final class RepositorioDePedidosJdbc implements RepositorioDePedidos {
    private final JdbcClient jdbc;
    // buscar(...) y guardar(...) con SQL y conversión fila ⇄ Pedido
}

// adaptador de entrada: un controlador web que solo traduce
@RestController
class PedidosController {
    private final CancelarPedido cancelarPedido;

    @PostMapping("/pedidos/{id}/cancelacion")
    ResponseEntity<Void> cancelar(@PathVariable UUID id) {
        cancelarPedido.cancelar(new PedidoId(id));
        return ResponseEntity.noContent().build();
    }
}

Y la recompensa: el caso de uso se prueba con un adaptador en memoria, sin Spring ni base de datos.

var pedidos = new RepositorioDePedidosEnMemoria();   // otro adaptador del mismo puerto
pedidos.guardar(Pedido.nuevo(ID));

new CancelarPedidoServicio(pedidos).cancelar(ID);

assertThat(pedidos.buscar(ID).orElseThrow().estado()).isEqualTo(CANCELADO);

Para que la regla de dependencias no dependa de la buena voluntad, conviene comprobarla automáticamente: con módulos separados (Maven, Gradle, paquetes de npm), donde un import prohibido ni compila, o con ArchUnit, una librería de Java que convierte la regla en una prueba:

@ArchTest
static final ArchRule nucleoSinFramework = noClasses()
        .that().resideInAPackage("..dominio..")
        .should().dependOnClassesThat().resideInAnyPackage("org.springframework..", "java.sql..");

Casos reales de código abierto

  • Kopi Chess, en Java 25 y Spring Boot 4: un módulo Maven por anillo (dominio, aplicación, un módulo por adaptador y el arranque), reglas de ArchUnit, casos de uso sin anotaciones de Spring, un puerto implementado por dos adaptadores (bots propios y Stockfish) y métricas añadidas con decoradores de los puertos. Explicado paso a paso en Aprendizajes de Kopi Chess.
  • Prompt Quest, en TypeScript y serverless en AWS: los mismos puertos (almacén, cola, compilador con IA) tienen adaptadores locales con ficheros y adaptadores de AWS, así que el juego entero funciona en local sin nube. Explicado en Aprendizajes de Prompt Quest.

Errores frecuentes

  • Puertos que reflejan la tecnología: usar como puerto un JpaRepository o un cliente del SDK de la nube mete la tecnología en el núcleo por la puerta de atrás. El puerto se diseña desde lo que necesita el caso de uso, no desde lo que ofrece la librería.
  • Anotaciones del framework en el dominio: entidades con @Entity o servicios con @Transactional atan el núcleo a JPA o a Spring. Si se acepta como compromiso práctico, que sea una decisión consciente y escrita.
  • Lógica de negocio en los adaptadores: un controlador que decide si un pedido se puede cancelar, o una consulta SQL que aplica una regla de negocio, dejan esa regla fuera del alcance de las pruebas rápidas.
  • Adaptadores que se llaman entre sí: el controlador web que usa directamente el repositorio se salta el caso de uso. Todo pasa por el núcleo.
  • Ceremonia donde no hay dominio: en una aplicación que solo guarda y lee formularios (un CRUD), los puertos, los mapeos y los módulos cuestan más de lo que aportan.
  • Un puerto por tabla: los puertos agrupan conversaciones del negocio; no tienen por qué coincidir con el modelo de datos.
  • Dejar la regla sin comprobar: con el tiempo aparecen los import prohibidos. Módulos o pruebas de arquitectura evitan que la estructura se degrade.

Hexagonal, capas, cebolla y arquitectura limpia

CapasHexagonalLimpia / cebolla
ImagenPresentación sobre negocio sobre datos.Un núcleo con puertos y adaptadores alrededor.Círculos concéntricos: entidades, casos de uso, adaptadores, frameworks.
Dirección de las dependenciasHacia abajo: el negocio suele depender de la capa de datos.Hacia dentro: los adaptadores dependen del núcleo.Hacia dentro, igual que la hexagonal.
Qué aportaSencillez y orden en aplicaciones pequeñas.La simetría: interfaz, base de datos y pruebas son «el exterior» por igual.Más anillos con nombre y reglas más detalladas.

Las tres últimas comparten la idea central (la regla de dependencias y la inversión de dependencias); cambian sobre todo el dibujo y el vocabulario. En la práctica, muchos equipos dicen «hexagonal» y aplican una mezcla.

Cuándo elegirla: cuando hay lógica de negocio que merece protegerse y probarse sola, cuando se espera cambiar o añadir tecnologías (otra base de datos, otro canal de entrada) o cuando varias entradas usan los mismos casos de uso (web, API, mensajes). Cuándo no: en un CRUD sencillo, un prototipo de usar y tirar o un script.
