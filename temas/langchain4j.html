Qué es

LangChain4j es una biblioteca de Java para usar modelos de lenguaje desde una aplicación: enviarles mensajes, recibir respuestas con forma de objeto Java, dejar que pidan ejecutar herramientas, recordar la conversación o buscar en documentos propios (RAG). Es software libre, nació en 2023 inspirada en LangChain (de Python) y desde 2025 está en la línea 1.x, con una API estable.

Su idea central es que no tengas que escribir peticiones HTTP a cada proveedor: declaras una interfaz Java y la biblioteca genera la implementación que habla con el modelo, sea de OpenAI, Anthropic, Google, Mistral, Ollama o un despliegue en la nube.

Vocabulario para empezar

  • Proveedor: la empresa o plataforma que sirve el modelo por una API (OpenAI, Anthropic, Azure, Amazon Bedrock…). Cada uno tiene su formato de petición.
  • Mensaje de sistema: instrucciones fijas que el modelo recibe antes del mensaje del usuario (quién es, qué puede hacer, en qué formato responder). Ver ingeniería de prompts.
  • Memoria de chat: los mensajes anteriores de una conversación, que hay que reenviar en cada llamada porque el modelo no recuerda nada por sí mismo.

Por qué importa

La mayoría de aplicaciones de empresa están en Java, y llamar a un LLM a mano obliga a resolver siempre lo mismo: el formato de cada proveedor, convertir el JSON de respuesta en objetos, el bucle de herramientas, la memoria, los reintentos. LangChain4j lo resuelve una vez y deja cambiar de proveedor tocando la configuración, no el código. Tiene integraciones oficiales con Spring Boot y con Quarkus (la extensión Quarkus LangChain4j).

Conceptos clave

  • ChatModel: la interfaz de bajo nivel que representa un modelo de chat de un proveedor concreto (OpenAiChatModel, AnthropicChatModel…). Recibe mensajes y devuelve una respuesta. Hasta la 1.0 se llamaba ChatLanguageModel.
  • AI Services: el nivel alto. Una interfaz anotada con @SystemMessage y @UserMessage (con variables {{nombre}} que se rellenan con parámetros marcados con @V). AiServices.create(...) genera la implementación.
  • Salida estructurada: si el método de la interfaz devuelve un record o un enum en lugar de String, LangChain4j pide al modelo un JSON con esa forma y lo convierte. Ver Structured Outputs.
  • Herramientas: métodos Java anotados con @Tool (y sus parámetros con @P, que lleva la descripción). El modelo puede pedir ejecutarlos; la biblioteca los ejecuta y le devuelve el resultado. Ver Tool Calling.
  • ChatMemory: guarda la conversación con una política de ventana (los últimos N mensajes o los últimos N tokens). Con @MemoryId se separa por usuario o por sesión.
  • RAG: piezas para trocear documentos, calcular embeddings, guardarlos en un almacén vectorial y recuperar los fragmentos relevantes antes de preguntar.

En la práctica

Un servicio que clasifica un texto en una categoría, devolviendo un objeto:

enum Linea { MUJER, HOMBRE, NINA, NINO, NINGUNA }

record Clasificacion(Linea linea, String motivo) {}

interface Clasificador {
    @SystemMessage("Clasifica el texto del usuario en una línea de producto. Si no se puede saber, usa NINGUNA.")
    Clasificacion clasificar(@UserMessage String texto);
}

ChatModel modelo = OpenAiChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .modelName("gpt-5-mini")
        .build();

Clasificador clasificador = AiServices.create(Clasificador.class, modelo);
Clasificacion c = clasificador.clasificar("vestidos de fiesta para ella");

Con Quarkus LangChain4j no se construye nada a mano: la interfaz lleva @RegisterAiService y el modelo sale de la configuración. Se pueden declarar varios modelos con nombre (@ModelName("clasificador")), cada uno con su proveedor, modelo y límites:

quarkus:
  langchain4j:
    clasificador:
      chat-model:
        provider: openai
    openai:
      clasificador:
        chat-model:
          model-name: gpt-5-mini
          max-completion-tokens: 4000

Cuando hay más de una extensión de proveedor en el proyecto (por ejemplo, OpenAI y Anthropic), cada modelo con nombre tiene que decir su provider; si falta, la aplicación no arranca.

LangChain4j o Spring AI

Spring AI resuelve lo mismo con el estilo de Spring (un ChatClient fluido, autoconfiguración por propiedades). LangChain4j es independiente del framework, tiene las interfaces declarativas como pieza principal y funciona igual en Spring, en Quarkus o sin framework. En un proyecto Spring puro, Spring AI encaja de forma más natural; en Quarkus, o si se quiere no atarse a Spring, LangChain4j es la opción habitual.

Errores frecuentes

  • Límite de tokens de salida demasiado bajo: los modelos de razonamiento gastan parte de ese límite «pensando»; si se acaba, la respuesta llega cortada y el JSON no se puede convertir. Dale margen y vigila el motivo de fin de la respuesta.
  • Confiar ciegamente en la salida: aunque se pida un enum, valida en código lo que llega antes de usarlo para algo importante.
  • Descripciones de herramientas pobres: el modelo decide llamarlas solo por su nombre y su descripción; si son ambiguas, no las usa o las usa mal.
  • Memoria compartida entre usuarios: sin @MemoryId, todos los usuarios comparten la misma conversación.
  • Registrar peticiones y respuestas en producción: los registros de depuración (log-requests, log-responses) pueden contener datos personales. Actívalos solo en local.
  • Copiar ejemplos de versiones 0.x: varios nombres cambiaron en la 1.0 (ChatLanguageModel pasó a ChatModel).
