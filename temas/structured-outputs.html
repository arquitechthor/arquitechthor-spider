Qué es

Las salidas estructuradas (Structured Outputs) son la capacidad de una API de modelo de lenguaje de devolver la respuesta en un formato fijo y verificable, normalmente un JSON que cumple un esquema que le das tú, en lugar de texto libre. Así el programa que llama puede leer la respuesta como datos (datos estructurados) sin adivinar dónde empieza y dónde acaba cada cosa.

Hay tres niveles, de menos a más fiable: pedirlo en el prompt («responde solo con JSON»), el modo JSON (la API garantiza que la respuesta es JSON válido, pero no su forma) y el esquema estricto (la API garantiza que el JSON cumple tu esquema: campos, tipos y valores permitidos).

Vocabulario para empezar

  • JSON Schema: un estándar para describir la forma de un JSON: qué campos tiene, de qué tipo es cada uno, cuáles son obligatorios y qué valores admite (por ejemplo, una lista cerrada con enum).
  • Decodificación restringida: la técnica que usa el proveedor para cumplir el esquema: mientras el modelo genera cada token, se descartan los que harían que el JSON dejara de encajar.
  • Motivo de fin: el campo de la respuesta que dice por qué paró el modelo: porque terminó, porque llegó al límite de tokens o porque se negó.

Por qué importa

En cuanto la respuesta de un LLM alimenta código (guardar una regla, rellenar un formulario, decidir el siguiente paso de un agente), el texto libre es un riesgo: un campo con otro nombre, una coma de más o una frase de cortesía antes del JSON rompen el programa. Con un esquema estricto, esos fallos desaparecen y el código que valida puede centrarse en el significado (¿este valor tiene sentido?) en lugar de en la forma.

Conceptos clave

  • Forma no es verdad: el esquema garantiza que el campo categoria existe y es un número, no que sea la categoría correcta. Un modelo puede devolver un JSON perfecto con datos inventados (ver alucinaciones).
  • Listas cerradas: un enum en el esquema es la forma más eficaz de que el modelo elija entre opciones válidas en vez de inventar valores. Aun así, conviene comprobarlas en código.
  • Restricciones del modo estricto: los proveedores solo admiten una parte de JSON Schema. En el de OpenAI, por ejemplo, todos los campos tienen que ser obligatorios (lo opcional se expresa permitiendo null) y hay que prohibir campos extra con additionalProperties: false.
  • Respuesta cortada: si el modelo llega al límite de tokens de salida antes de cerrar el JSON, la respuesta es inválida aunque el modo estricto estuviera activado. Se detecta por el motivo de fin (length en OpenAI, max_tokens en Anthropic).
  • Negativas: si el modelo rechaza responder por seguridad, algunas APIs lo indican en un campo aparte (refusal) en lugar de rellenar el esquema.
  • Herramientas como alternativa: antes de existir el modo estricto, el truco habitual era definir una herramienta con el esquema deseado y obligar al modelo a llamarla: sus argumentos eran la salida estructurada.

En la práctica

Un esquema para que el modelo devuelva un estado, una lista de códigos válidos y una pregunta opcional:

{
  "type": "object",
  "properties": {
    "status":   { "type": "string", "enum": ["OK", "AMBIGUOUS", "NOT_FOUND"] },
    "codes":    { "type": "array", "items": { "type": "string", "enum": ["A", "B", "C"] } },
    "question": { "type": ["string", "null"] }
  },
  "required": ["status", "codes", "question"],
  "additionalProperties": false
}

Con LangChain4j o Spring AI no se escribe el esquema a mano: se genera a partir de un record Java. Lo que sí hay que escribir es la validación posterior, porque el modelo puede seguir equivocándose dentro del formato:

record Respuesta(String status, List<String> codes, String question) {}

Respuesta r = servicio.traducir(mensaje);
if (r == null || r.status() == null) {
    return Resultado.error();                 // no se puede interpretar: no adivinar
}
List<String> validos = r.codes().stream()
        .filter(CODIGOS_PERMITIDOS::contains)  // descarta lo que no existe
        .distinct()
        .toList();

Una regla útil: si la respuesta no se puede interpretar, devuelve un estado de error explícito, distinto de «no encontrado». Confundirlos puede hacer que un fallo del modelo se trate como «sin filtro» y la decisión se aplique a todo.

Errores frecuentes

  • Pedir JSON solo en el prompt: funciona casi siempre, que es peor que nunca: los fallos llegan a producción. Usa el modo estricto si el proveedor lo ofrece.
  • Límite de salida justo: con modelos de razonamiento, el pensamiento consume tokens del mismo límite. Revisa el motivo de fin antes de convertir el JSON.
  • Objeto vacío como «nada»: unos modelos devuelven null y otros {} cuando no hay resultado. Trata los dos igual en código.
  • Saltarse la validación: el esquema no sabe qué valores existen en tu base de datos. Comprueba los identificadores contra la fuente real.
  • Esquemas enormes: cuantos más campos y niveles, más tokens y más errores. Pide solo lo que vas a usar.
  • Mostrar la respuesta cruda al usuario cuando falla: registra el detalle para depurar y enseña un mensaje controlado.
