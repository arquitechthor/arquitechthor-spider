Qué es

Spring AI es el proyecto del ecosistema Spring para usar modelos de IA desde aplicaciones Java. Da una API común para hablar con muchos proveedores (Anthropic, OpenAI, Google, Amazon, Microsoft, Ollama para modelos locales…) y trae hechas las piezas que casi toda aplicación con un LLM acaba necesitando: prompts con plantillas, respuestas convertidas en objetos Java, herramientas, memoria de la conversación, embeddings, bases vectoriales, RAG, MCP, métricas y evaluación.

La idea es la de siempre en Spring: igual que Spring Data esconde los detalles de cada base de datos, Spring AI esconde los de cada proveedor de modelos. Añades un starter (una dependencia que trae todo lo necesario), configuras unas propiedades y Spring Boot crea los beans (los objetos que gestiona Spring) listos para inyectar en tus clases.

Por qué importa

Buena parte del backend de empresa está escrito en Java con Spring. Spring AI permite añadirle capacidades de lenguaje (resumir, clasificar, extraer datos, responder sobre documentos, automatizar tareas con agentes) sin montar un servicio aparte en Python, y con lo que ya usa el resto de la aplicación: inyección de dependencias, configuración por propiedades, pruebas, seguridad y métricas.

Al ser portable, cambiar de proveedor o de modelo es sobre todo cambiar una dependencia y unas propiedades, no reescribir el código. La versión 1.0 salió en mayo de 2025 y la 2.0 en junio de 2026; esta ficha describe la 2.x, pensada para Spring Boot 4 y Spring Framework 7. Los proyectos que siguen en Spring Boot 3 usan la 1.x.

Conceptos clave

  • ChatModel: la interfaz de bajo nivel para hablar con un modelo de chat. Cada proveedor tiene su implementación: recibe un Prompt (la lista de mensajes) y devuelve la respuesta.
  • ChatClient: la API de alto nivel que se usa a diario, encadenando métodos al estilo de RestClient: prompt(), system(), user(), call() o stream() y content(). Se crea con un ChatClient.Builder en el que se fijan los valores por defecto: prompt de sistema (las instrucciones generales del modelo), herramientas y advisors.
  • Salida estructurada: entity(Clase.class) convierte la respuesta en un objeto Java (por ejemplo un record). Spring AI indica al modelo el formato JSON esperado, o usa la salida estructurada nativa del proveedor, y convierte el resultado.
  • Herramientas: métodos anotados con @Tool (con una descripción) y sus parámetros con @ToolParam, que se pasan con tools(...). El modelo no ejecuta nada: pide la llamada, Spring AI ejecuta el método y le devuelve el resultado, en bucle hasta que el modelo responde (ver Tool Calling).
  • Advisors: interceptores que actúan antes y después de cada llamada, como los filtros de una aplicación web. Pueden añadir el historial a la petición, buscar documentos o filtrar contenido. Vienen hechos, entre otros, MessageChatMemoryAdvisor (memoria), QuestionAnswerAdvisor y RetrievalAugmentationAdvisor (RAG) y SafeGuardAdvisor (bloquea palabras sensibles).
  • Memoria de chat: las API de los modelos no recuerdan nada entre peticiones. ChatMemory guarda los mensajes de cada conversación (en memoria o en una base de datos) y un advisor los añade a cada llamada.
  • Embeddings y VectorStore: un embedding es una lista de números que representa el significado de un texto; textos parecidos dan vectores cercanos. EmbeddingModel los calcula y VectorStore es una API común sobre bases vectoriales (PGVector, Qdrant, Redis, Milvus, Elasticsearch…) para guardarlos y buscar los más parecidos, con filtros por metadatos.
  • ETL de documentos: lectores (PDF, texto, JSON…), troceado y carga en el VectorStore: el paso previo de cualquier RAG.
  • MCP: cliente para usar herramientas de servidores MCP y servidor para ofrecer las de tu aplicación a otros agentes. En la 2.x forma parte del núcleo y se apoya en el SDK oficial de MCP para Java. Las herramientas de un servidor MCP no se añaden solas al ChatClient: se le pasan con tools(...) o defaultTools(...).
  • Observabilidad y evaluación: métricas y trazas con Micrometer (la biblioteca de métricas de Spring: tokens gastados, tiempos) y utilidades para comprobar en pruebas si las respuestas son relevantes y se apoyan en el contexto dado.

En la práctica

1. Dependencias. Se importa el BOM spring-ai-bom (fija versiones compatibles de todos los módulos) y se añade el starter del proveedor, que sigue el patrón spring-ai-starter-model-<proveedor>:

<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>

2. Propiedades. Cada proveedor tiene su prefijo. La clave, siempre desde una variable de entorno o un gestor de secretos, nunca en el repositorio:

spring.ai.openai.api-key=${OPENAI_API_KEY}

3. Código. Un controlador de soporte con prompt de sistema y una herramienta que consulta pedidos:

@RestController
class SoporteController {

  private final ChatClient chat;

  SoporteController(ChatClient.Builder builder, Pedidos pedidos) {
    this.chat = builder
        .defaultSystem("Eres el asistente de una tienda. Responde en español y con brevedad.")
        .defaultTools(pedidos)
        .build();
  }

  @GetMapping("/soporte")
  String preguntar(@RequestParam String pregunta) {
    return chat.prompt().user(pregunta).call().content();
  }
}

@Component
class Pedidos {

  @Tool(description = "Devuelve el estado de un pedido a partir de su número")
  String estado(@ToolParam(description = "Número de pedido") String numero) {
    return repositorio.estadoDe(numero);   // tu código de siempre
  }
}

Para recibir datos en vez de texto, basta con cambiar el final de la cadena:

record Ticket(String categoria, int urgencia, String resumen) {}

Ticket t = chat.prompt().user(correo).call().entity(Ticket.class);

Errores frecuentes

  • Creer que el modelo recuerda la conversación: sin ChatMemory cada petición empieza de cero. Y con ella, limita cuántos mensajes se envían: cada uno se paga en tokens y ocupa ventana de contexto (el texto máximo que el modelo atiende a la vez).
  • Fiarse a ciegas de entity(): el objeto puede llegar con campos vacíos o valores absurdos. Valídalo como cualquier entrada externa y decide qué hacer si falla.
  • Herramientas peligrosas sin control: el modelo decide cuándo llamarlas, y un texto malicioso puede empujarle a hacerlo (inyección de prompt). Comprueba permisos dentro del método y pide confirmación antes de acciones irreversibles.
  • Descripciones vagas: el modelo elige herramienta por su nombre y descripción; si no dicen qué hace y cuándo usarla, la usará mal o no la usará.
  • Mezclar versiones: gestiona todos los módulos con el BOM. La 2.x necesita Spring Boot 4, y muchos tutoriales antiguos usan nombres de artefactos anteriores a la 1.0 (como spring-ai-openai-spring-boot-starter) que ya no existen.
  • No medir: sin las métricas de tokens y tiempos el coste llega por sorpresa en la factura. Actívalas desde el principio (ver Cost & Latency).

Spring AI o LangChain4j

Las dos son bibliotecas Java maduras, con muchos proveedores, herramientas, RAG y MCP. La diferencia está en el encaje y en el estilo:

Spring AILangChain4j
OrigenProyecto oficial de Spring.Proyecto independiente, inspirado al principio en LangChain (Python).
EstiloChatClient encadenado y advisors.AI Services: escribes una interfaz Java anotada y la biblioteca la implementa.
MarcoPensado para Spring Boot (autoconfiguración, propiedades, Micrometer).Sin dependencia de un marco, con integraciones para Spring Boot, Quarkus y otros.
CuándoTu aplicación ya es Spring Boot y quieres sus convenciones.No usas Spring, usas Quarkus o prefieres el estilo declarativo.
