Qué es

SOLID es el nombre de cinco principios de diseño para escribir código orientado a objetos que se pueda cambiar sin miedo: que añadir una funcionalidad no obligue a tocar medio programa, que un arreglo en un sitio no rompa otro y que cada pieza se pueda probar por separado. Cada letra es un principio:

  • S: principio de responsabilidad única (SRP).
  • O: principio abierto/cerrado (OCP).
  • L: principio de sustitución de Liskov (LSP).
  • I: principio de segregación de interfaces (ISP).
  • D: principio de inversión de dependencias (DIP).

Los reunió Robert C. Martin («Uncle Bob») a finales de los años noventa, a partir de ideas que venían de antes: el abierto/cerrado es de Bertrand Meyer (1988) y la sustitución, de Barbara Liskov (1987). El acrónimo no es suyo: según el propio Martin, lo propuso Michael Feathers hacia 2004, y forma la palabra inglesa solid («sólido»).

Para seguir la ficha bastan tres palabras. Un módulo es una unidad de código con sentido propio: una clase, un paquete o un fichero. Una interfaz es un contrato: la lista de operaciones que algo ofrece, sin decir cómo las hace; en Java, un interface. Y una dependencia es que un módulo necesite a otro: si la clase A usa la clase B (la crea, la llama o la nombra en su código), A depende de B, y un cambio en B puede obligar a cambiar A.

Por qué importa

Casi todo el coste de un programa llega después de escribirlo, al cambiarlo. Los cinco principios atacan la causa más común de que cambiar sea caro: el acoplamiento, es decir, que las piezas dependan demasiado unas de otras (ver alta cohesión y bajo acoplamiento). Por eso son la base de casi todo lo que viene después: los patrones de diseño, la inyección de dependencias de Spring, la arquitectura hexagonal o la arquitectura limpia son SOLID aplicado a mayor escala.

También son una pregunta clásica de entrevista para perfiles backend, y un vocabulario compartido en las revisiones de código: «esta clase tiene dos razones para cambiar» o «esta interfaz obliga a implementar métodos que no usa» se entienden sin más explicación.

S: responsabilidad única

La formulación más conocida es que un módulo debe tener una sola razón para cambiar. Martin la aclaró en 2014 porque se malinterpretaba mucho: no significa «hacer una sola cosa» (eso es otra regla, para funciones), sino que el módulo responde ante una sola persona o un solo grupo que pide cambios. Su versión más práctica: junta lo que cambia por las mismas razones y separa lo que cambia por razones distintas.

Su ejemplo es una clase Empleado con tres métodos: calcular la nómina (lo pide finanzas), guardarse en la base de datos (lo decide el equipo técnico) y generar el informe de horas (lo pide operaciones). Son tres responsabilidades porque son tres jefes distintos: un cambio pedido por finanzas puede romper el informe de operaciones, que no pidió nada.

// Antes: tres razones para cambiar en una clase
class Empleado {
    Dinero calcularNomina() { … }        // finanzas
    void guardar() { … }                  // equipo técnico (SQL, tablas)
    String informeDeHoras() { … }         // operaciones
}

// Después: cada clase responde ante un solo grupo
record Empleado(String id, String nombre, Contrato contrato) {}
class CalculadoraDeNominas { Dinero calcular(Empleado e) { … } }
class RepositorioDeEmpleados { void guardar(Empleado e) { … } }
class InformeDeHoras { String generar(Empleado e) { … } }

Señales de alarma: una clase que cambia en casi todos los commits, un nombre genérico (Gestor, Utilidades, Servicio a secas) o una prueba que necesita preparar una base de datos para comprobar un cálculo.

O: abierto/cerrado

Un módulo debe estar abierto a la extensión y cerrado a la modificación: se le puede añadir comportamiento nuevo sin editar el código que ya funciona. Meyer lo propuso en 1988 pensando en la herencia; hoy se consigue sobre todo con interfaces y polimorfismo, es decir, haciendo que el código trabaje contra un contrato y que cada variante sea una clase que lo cumple. Martin lo resume en que el comportamiento de un sistema debería poder ampliarse sin modificar ese sistema, como hace una arquitectura de plugins.

// Cerrado a la modificación: este método no cambia al añadir medios de pago
interface MedioDePago { Recibo cobrar(Dinero importe); }

final class Caja {
    Recibo cobrar(Dinero importe, MedioDePago medio) { return medio.cobrar(importe); }
}

// Abierto a la extensión: un medio nuevo es una clase nueva
final class PagoConBizum implements MedioDePago { … }

Lo contrario es la cadena de if o de switch sobre un tipo que se repite por el código: cada caso nuevo obliga a encontrar y editar todas las copias. Dos técnicas habituales para cumplirlo son el patrón estrategia (cada variante es un objeto intercambiable, como MedioDePago) y el decorador (una clase envuelve a otra con la misma interfaz y le añade algo, por ejemplo medir o registrar, sin tocarla); ver patrones de comportamiento y patrones estructurales.

No es una regla absoluta. Ningún código está cerrado frente a todos los cambios posibles: hay que elegir frente a cuáles cerrarse. A veces lo mejor es justo lo contrario, como se ve en el caso de Kopi Chess más abajo.

L: sustitución de Liskov

Si un programa funciona con un tipo, debe seguir funcionando igual con cualquier subtipo suyo (una clase que lo extiende o una implementación de una interfaz), sin que el programa tenga que saber cuál le ha tocado. Barbara Liskov lo planteó en 1987, y en 1994 lo formalizó con Jeannette Wing. Martin insiste en que no va de herencia sino de contratos: quien usa una interfaz no debe llevarse sorpresas con ninguna implementación.

Para no romper el contrato, un subtipo:

  • No puede pedir más que el tipo original (no endurecer las precondiciones, lo que se exige antes de llamar). Si el contrato acepta cualquier importe positivo, una implementación que rechace los mayores de 100 € lo rompe.
  • No puede prometer menos (no debilitar las postcondiciones, lo que se garantiza al terminar). Si el contrato promete devolver una lista ordenada, una implementación que a veces la devuelva desordenada lo rompe.
  • Debe mantener las reglas que siempre se cumplen (los invariantes) y no lanzar errores que el contrato no anuncia.

El ejemplo clásico es el cuadrado que hereda del rectángulo. Matemáticamente un cuadrado «es un» rectángulo, pero en código no lo es si el rectángulo deja cambiar ancho y alto por separado:

void probar(Rectangulo r) {
    r.setAncho(5);
    r.setAlto(4);
    assert r.area() == 20;   // falla si r es un Cuadrado: al fijar el alto, cambia también el ancho
}

El código compila y la herencia es correcta para el compilador, pero el comportamiento no lo es. Por eso LSP no se comprueba con el compilador sino con pruebas: si las mismas pruebas del contrato pasan con todas las implementaciones, son intercambiables.

I: segregación de interfaces

Ningún cliente debería depender de métodos que no usa. Mejor varias interfaces pequeñas, pensadas para quien las usa, que una grande para todos. Se cuenta que Martin lo formuló trabajando como consultor para Xerox: una sola clase de «trabajo» de impresora servía para imprimir, grapar y enviar faxes, y cualquier cambio obligaba a recompilar y desplegar todo, aunque una tarea de grapado no usara nada de la impresión.

// Una interfaz grande obliga a todos a implementarlo todo
interface Multifuncion { void imprimir(Doc d); void escanear(Doc d); void enviarFax(Doc d); }

// Mejor: cada cliente depende solo de lo que usa
interface Impresora { void imprimir(Doc d); }
interface Escaner   { void escanear(Doc d); }
final class ImpresoraSencilla implements Impresora { … }   // sin métodos vacíos ni excepciones de "no soportado"

Señal de alarma: implementaciones llenas de métodos vacíos o que lanzan UnsupportedOperationException; eso además suele romper la sustitución de Liskov.

D: inversión de dependencias

Tiene dos partes: los módulos de alto nivel (las reglas de negocio) no deben depender de los de bajo nivel (la base de datos, la red, un framework), sino ambos de abstracciones; y las abstracciones no deben depender de los detalles, sino al revés.

Se llama «inversión» porque da la vuelta a la dirección natural. Sin aplicarlo, el servicio de pedidos usa directamente la clase que habla con PostgreSQL, y depende de ella. Aplicándolo, el servicio define la interfaz que necesita (RepositorioDePedidos) y la clase de PostgreSQL la implementa: ahora es el detalle el que depende del negocio.

// Alto nivel: define lo que necesita, sin saber cómo se hace
interface RepositorioDePedidos { void guardar(Pedido p); }

final class ServicioDePedidos {
    private final RepositorioDePedidos pedidos;
    ServicioDePedidos(RepositorioDePedidos pedidos) { this.pedidos = pedidos; }   // se lo dan hecho
}

// Bajo nivel: implementa la abstracción del alto nivel
final class RepositorioDePedidosPostgres implements RepositorioDePedidos { … }

No hay que confundirla con la inyección de dependencias, aunque vayan juntas: la inversión es una regla sobre hacia dónde apuntan las dependencias; la inyección es una técnica para entregar a cada objeto las piezas que necesita (por el constructor, como arriba) en lugar de que las cree él. Spring hace la inyección; la inversión la decide quien diseña.

Cómo encajan entre sí

Los cinco se refuerzan. Las interfaces pequeñas (I) son más fáciles de implementar bien (L) y de usar como frontera entre el negocio y los detalles (D). Esas fronteras permiten añadir variantes sin tocar el núcleo (O). Y separar responsabilidades (S) es lo que hace que cada interfaz salga pequeña. Aplicados a la arquitectura entera, dan exactamente los puertos y adaptadores de la arquitectura hexagonal.

Caso real: Kopi Chess

Kopi Chess (código público, Java 25 y Spring Boot 4) tiene un ejemplo de cada principio. Su backend sigue la arquitectura hexagonal: un dominio con las reglas del ajedrez, una capa de aplicación con los casos de uso y los puertos (las interfaces que necesita) y un módulo por cada adaptador (web, PostgreSQL, Stockfish…). Explicado con más detalle y con el código completo en Kopi Chess, un caso de estudio de SOLID.

S: Stockfish, repartido en cuatro clases

Hablar con Stockfish (el motor de ajedrez que analiza las partidas) podría ser una sola clase. Kopi Chess lo reparte en cuatro, cada una con su razón para cambiar: UciProcess lanza el proceso y lee su salida; UciConnection es la conversación por líneas (entra un comando, salen líneas); UciEngine es el protocolo UCI (qué se envía y qué respuesta se espera); y EnginePool presta un motor a cada llamada. La recompensa se ve en las pruebas: UciEngine se prueba con una conexión simulada, sin instalar Stockfish. (código)

Lo mismo pasa con el análisis: AnalysisRepository solo guarda los análisis terminados, y su comentario dice que si un análisis está en cola, en marcha o ha fallado es asunto de otra interfaz, AnalysisJobQueue. Y cada caso de uso es una clase: PlayMove, Resign, AgreeDraw…

O: decoradores que miden sin tocar nada

Los bots y los casos de uso no saben nada de métricas. Para medir cuánto tarda cada bot en mover, Kopi Chess añade un decorador, TimedBotPlayer, que cumple la misma interfaz BotPlayer, envuelve al bot real y cronometra cada jugada. Se añadió comportamiento sin editar ni los bots ni los casos de uso:

final class TimedBotPlayer implements BotPlayer {
    private final BotPlayer bot;            // el bot de verdad
    private final MeterRegistry registry;   // Micrometer, solo aquí

    @Override
    public Move chooseMove(Position position, BotProfile profile) {
        var sample = Timer.start(registry);
        // … llama a bot.chooseMove(position, profile) y para el cronómetro en un finally
    }
}

(TimedBotPlayer.java; LoggedAnalysisJobQueue y TimedAnalysisRepository hacen lo mismo con sus interfaces.) Y en la configuración, los bots propios (Peón y Caballo) y Stockfish (Alfil, Torre y Dama) se combinan detrás del mismo BotPlayer: los casos de uso no saben quién juega.

El contraejemplo, a propósito: los tipos de jugada (normal, captura, enroque, al paso, promoción…) son una interfaz sellada (sealed, solo admite las implementaciones que ella enumera), y aplicar una jugada es un switch sobre todos ellos. Añadir un tipo obligaría a modificar ese switch, y es lo que se quiere: las reglas del ajedrez no cambian, y si alguien olvida un caso, el código no compila. Cerrarse frente a cambios que no van a llegar no aporta nada.

L: dos repositorios que cumplen el mismo contrato

La interfaz GameRepository promete un bloqueo optimista: update(partida, versionCargada) solo guarda si la partida sigue en la versión que se leyó, y si no, lanza ConcurrentGameUpdateException. Así, si dos peticiones mueven a la vez, una falla en lugar de pisar a la otra. Lo cumplen la implementación real con PostgreSQL y la de memoria que usan las pruebas:

// En memoria, para las pruebas de los casos de uso
public void update(Game game, long loadedVersion) {
    var stored = games.get(game.id());
    if (stored == null || stored.version() != loadedVersion) {
        throw new ConcurrentGameUpdateException(game.id(), loadedVersion);
    }
    games.put(game.id(), game);
}

// Con PostgreSQL: el mismo contrato, con "where id = :id and version = :loadedVersion"
if (updated == 0) {
    throw new ConcurrentGameUpdateException(game.id(), loadedVersion);
}

Por eso las pruebas de PlayMove hechas con la versión en memoria valen también para producción. Una versión en memoria que guardara sin comprobar la versión compilaría igual, pero rompería la promesa de «si hay conflicto, no se guarda nada». (GameRepository.java)

Un matiz útil: KopiBots lanza BotUnavailableException si le piden un bot que no es suyo, y eso no rompe la sustitución, porque el contrato de BotPlayer ya anuncia esa excepción. Lo que rompe a Liskov es la sorpresa, no la excepción.

I: una interfaz por caso de uso

Cada caso de uso tiene su propia interfaz con un solo método: PlayMoveUseCase.play(…), ResignUseCase, ListGamesUseCase… Un controlador pide solo las que usa. Y los puertos también son pequeños: la cola de análisis, los resultados y los avisos de progreso son tres interfaces distintas, no un «servicio de análisis» con todo. El caso más claro es que elegir la jugada de un bot (BotPlayer) y analizar una posición (ChessEngine) son interfaces distintas aunque las dos las implemente el adaptador de Stockfish: el comentario del código lo justifica en que el bot más flojo no necesita motor y el análisis no necesita personalidad.

D: la aplicación define lo que necesita

Las interfaces viven en la capa de aplicación (application/port/) y las implementan los adaptadores: JdbcGameRepository, StockfishAnalysis, LichessOpeningBook… Todo se conecta en un solo sitio, la configuración del módulo de arranque. Y la regla no depende de la buena voluntad: una prueba con ArchUnit (una librería que comprueba la estructura del código) falla si el dominio o la aplicación dependen de un adaptador, de Spring o de java.sql.

static final ArchRule applicationDependsOnlyOnTheDomain = noClasses()
        .that().resideInAPackage(APPLICATION)
        .should().dependOnClassesThat().resideInAnyPackage(
                ADAPTERS, BOOTSTRAP, "org.springframework..", "jakarta..", "io.micrometer..", "java.sql..")
        .because("use cases must not depend on adapters or on Spring (ADR-002)");

(HexagonalArchitectureTest.java) Esa regla es la que obliga a que TimedBotPlayer viva en el módulo de arranque: la aplicación no puede ni ver Micrometer.

Errores frecuentes

  • Leer «responsabilidad única» como «un método por clase»: trocear sin criterio produce decenas de clases diminutas que hay que cambiar juntas. La pregunta es quién pide los cambios, no cuántas cosas hace.
  • Una interfaz para cada clase, por si acaso: una interfaz con una única implementación que nunca va a tener otra (ni siquiera en las pruebas) solo añade un salto al leer el código. Las interfaces se ponen en las fronteras que importan.
  • Abstraer por adelantado para cumplir el abierto/cerrado: diseñar puntos de extensión para cambios que nadie ha pedido. Choca con YAGNI; es mejor abrir el código cuando llega la segunda variante.
  • Usar la herencia para reutilizar código: heredar solo para aprovechar métodos lleva a subtipos que no cumplen el contrato del padre. Si no es sustituible, compón (ten un objeto dentro) en vez de heredar.
  • Confundir inversión con inyección de dependencias: usar Spring no garantiza la inversión. Si el servicio de negocio recibe inyectada la clase concreta de PostgreSQL, la dependencia sigue apuntando al detalle.
  • Tomarlos como leyes: son principios, y a veces chocan entre sí o con la simplicidad. Cada uno tiene un coste; se aplican donde el cambio es probable.

¿Siguen vigentes?

Hay críticas razonables: que nacieron con la orientación a objetos de los noventa, que con microservicios o con programación funcional importan menos, o que llevan a sobrediseñar (Dan North, por ejemplo, defiende sustituirlos por «escribe código sencillo»). Martin respondió en 2020 que el software sigue estando hecho de lo mismo y que la sencillez también necesita principios que la guíen. En la práctica, lo que perdura es la idea de fondo de cada uno, más allá del lenguaje: separar lo que cambia por motivos distintos, depender de contratos y no de detalles, y que los contratos sean pequeños y se cumplan.
