Qué es

Una eval (evaluación) es una prueba repetible que mide cómo de bien hace su trabajo una aplicación con LLM: se le pasa un conjunto de casos con la respuesta esperada y se cuenta cuántos acierta. El conjunto de casos de referencia, revisado por personas, se llama golden dataset (conjunto dorado).

Es el equivalente a las pruebas automáticas del software tradicional, adaptado a un componente que no es determinista: la misma pregunta puede recibir respuestas distintas, así que no basta con «pasa o no pasa» una vez; se mide un porcentaje.

Vocabulario para empezar

  • Caso: una entrada (la frase del usuario y su contexto) más lo esperado (la respuesta correcta, o los criterios que debe cumplir).
  • Umbral: el porcentaje mínimo de aciertos acordado para dar por buena una versión (por ejemplo, 90 % de aciertos y ningún valor inventado).
  • Regresión: cuando un cambio (en el prompt, el modelo o el código) empeora casos que antes funcionaban.
  • Temperatura: el parámetro que controla cuánto azar hay al elegir cada palabra. Con valores altos, las respuestas varían más entre ejecuciones (ver parámetros de muestreo).

Por qué importa

Sin evals, mejorar un prompt es ir a ciegas: arreglas el ejemplo que te han reportado y rompes otros tres sin enterarte. Con un conjunto fijo de casos, cada cambio se mide antes de desplegarse, se comparan modelos con números (cuál acierta más, cuál es más barato o más rápido) y se puede decir con datos si una funcionalidad de IA está lista. Muchos equipos lo resumen así: la eval es la especificación de lo que el sistema debe hacer.

Conceptos clave

  • Tipos de comprobación:
    • Exacta o por código: para salidas cerradas (una categoría, un código, un JSON). Barata y objetiva; úsala siempre que se pueda.
    • Por reglas: comprobar propiedades (que no invente campos, que el JSON sea válido, que la respuesta no pase de cierta longitud).
    • LLM como juez: otro modelo puntúa respuestas abiertas (¿es amable? ¿responde a lo pedido?) con una rúbrica. Útil, pero hay que comprobar de vez en cuando que el juez coincide con una persona.
    • Revisión humana: la referencia final, cara; se usa para construir el conjunto y calibrar al juez.
  • Cobertura del conjunto: al menos un caso por cada valor posible de la salida, más casos ambiguos, casos sin respuesta, varias respuestas a la vez y frases en los idiomas que usan los usuarios.
  • Repeticiones: ejecutar cada caso varias veces (por ejemplo, 3) para medir la reproducibilidad: un caso que acierta 2 de 3 veces es un problema aunque «haya pasado».
  • Métricas separadas: no todos los errores pesan igual. Inventar un valor que no existe es peor que no encontrar ninguno; cuéntalos por separado. Para clasificación sirven precisión y exhaustividad.
  • No sobreajustar: si ajustas el prompt mirando siempre los mismos casos, acabas aprobando el examen y no la asignatura. Reserva una parte del conjunto que no mires al ajustar.
  • Offline y online: offline es el conjunto fijo antes de desplegar; online es medir en producción (respuestas valoradas por usuarios, muestras revisadas, trazas). Los fallos reales de producción son la mejor fuente de casos nuevos.

En la práctica

Un conjunto de casos puede ser un simple fichero versionado junto al código:

[
  { "id": "C01", "entrada": "vestidos de mujer",          "esperado": { "estado": "OK", "codigos": ["M"] } },
  { "id": "C02", "entrada": "ropa para niños",            "esperado": { "estado": "AMBIGUO" } },
  { "id": "C03", "entrada": "camisetas de hombre y mujer", "esperado": { "estado": "OK", "codigos": ["H", "M"] } },
  { "id": "C04", "entrada": "todo el catálogo",           "esperado": { "estado": "NO_ENCONTRADO" } }
]

Y un ejecutor que lo recorre, llama al sistema real (no a un mock), compara y resume:

casos: 40   repeticiones: 3   aciertos: 112/120 (93,3 %)
inventados: 0   inestables (no 3/3): C02, C17   tiempo medio: 2,1 s

El resultado se guarda con la versión del prompt y del modelo, para poder comparar antes y después de cada cambio. Las evals que llaman a un modelo real cuestan dinero y tardan, así que no suelen ir en cada compilación: se ejecutan a mano o en un trabajo aparte de la integración continua, y las pruebas unitarias normales siguen usando dobles del modelo.

Errores frecuentes

  • Probar a mano con cuatro frases: da sensación de que funciona y no mide nada. Diez minutos escribiendo casos ahorran días de discusiones.
  • Solo casos fáciles: los fallos están en lo ambiguo, lo incompleto y lo raro. Inclúyelos a propósito.
  • Una sola ejecución: con temperatura mayor que cero, un acierto puede ser suerte. Repite.
  • Umbral sin acordar: sin un número decidido antes, cualquier resultado se puede defender. Acuérdalo con quien pide la funcionalidad.
  • Mezclar fallos de plataforma con fallos del modelo: un error 502 o un filtro de contenido no dicen nada de la calidad del prompt. Cuéntalos aparte.
  • Conjunto que no evoluciona: cada error real reportado debería convertirse en un caso nuevo.
