Qué es

Testcontainers es una biblioteca que permite a una prueba automática arrancar un servicio de verdad en un contenedor (una base de datos PostgreSQL, un broker de Kafka, un Redis, un servidor de correo falso), usarlo durante la prueba y tirarlo al terminar. Todo desde el propio código de la prueba: sin instalar nada a mano y sin compartir una base de datos con el resto del equipo.

Existe para muchos lenguajes (Java, Go, .NET, Node.js, Python…); esta ficha se centra en la versión de Java, que es la original. La línea actual es la 2.x: la 2.0, de octubre de 2025, quitó el soporte de JUnit 4 y renombró los módulos (más abajo, en «En la práctica»).

Vocabulario para empezar

  • Prueba de integración: la que comprueba que tu código funciona junto a otra pieza real (una base de datos, otro servicio), no aislado con sustitutos.
  • Docker e imagen: una imagen es un paquete con un programa y todo lo que necesita para ejecutarse (por ejemplo, postgres:18). Un contenedor es una imagen en marcha, aislada del resto del equipo. Docker es la herramienta más conocida para crearlos.
  • Desechable: que se crea limpio para las pruebas y se destruye al acabar, sin dejar datos ni procesos por ahí.
  • Doble de prueba: un sustituto falso de una dependencia (un repositorio en memoria, un mock). Útil para pruebas unitarias, pero no comprueba la pieza real.

Por qué importa

Antes de Testcontainers, las pruebas de integración solían elegir entre dos males:

  • Una base de datos compartida (la de desarrollo o una de pruebas): las pruebas de una persona pisaban los datos de otra, fallaban o pasaban según el día, y en la CI había que montarla aparte.
  • Una base de datos en memoria como H2 en lugar de la real: arranca rápido, pero no es PostgreSQL. Su SQL, sus tipos, sus restricciones y su forma de bloquear filas son distintos, así que una prueba puede pasar con H2 y el código fallar en producción, o al revés.

Testcontainers da lo mejor de los dos: el mismo motor y la misma versión que en producción, pero limpio y aislado en cada ejecución, en el portátil de cualquiera y en la CI, con el único requisito de tener Docker (o un entorno compatible) funcionando. Por eso se ha convertido en la forma habitual de probar contra servicios reales en Java, y Spring Boot lo integra de serie.

Cómo funciona

  1. La prueba declara el contenedor que necesita, con su imagen y versión.
  2. Testcontainers habla con Docker, descarga la imagen si no la tiene y arranca el contenedor.
  3. Espera a que esté listo (por ejemplo, a que PostgreSQL acepte conexiones), con una estrategia de espera que cada módulo trae configurada.
  4. Publica el puerto del servicio en un puerto aleatorio del equipo, para que no choque con nada que ya esté en marcha. La prueba pregunta la dirección real (getHost(), getMappedPort() o, en bases de datos, getJdbcUrl()).
  5. Al terminar, para el contenedor. Y por si el proceso de pruebas muere de golpe, un pequeño contenedor vigilante (Ryuk) borra todo lo que Testcontainers creó.

Hay módulos listos para los servicios más comunes (PostgreSQL, MySQL, MongoDB, Kafka, Redis, LocalStack para simular servicios de AWS…) y un GenericContainer para cualquier otra imagen.

Cuánto vive cada contenedor

Arrancar un contenedor cuesta unos segundos, así que decidir cuántas veces se arranca es lo que más influye en el tiempo de las pruebas:

  • Uno por prueba: máximo aislamiento, muy lento. Casi nunca compensa.
  • Uno por clase de pruebas: con JUnit 5, la anotación @Testcontainers en la clase y @Container en un campo static. Lo habitual en pruebas sencillas.
  • Uno para toda la ejecución (patrón singleton): se arranca una vez y lo comparten todas las clases. Es lo más rápido; a cambio, cada prueba debe dejar los datos como los encontró (o borrar las tablas al empezar).

Con Spring Boot hay una cuarta forma, muy cómoda: declarar el contenedor como un bean de una configuración de pruebas. Spring lo arranca con el contexto de la aplicación y, como reutiliza ese contexto entre clases de prueba con la misma configuración, el contenedor también se reutiliza.

Existe además el modo «reutilizable» (los contenedores sobreviven entre ejecuciones para acelerar el desarrollo local), pero es experimental y está pensado solo para el equipo de cada desarrollador, no para la CI.

En la práctica

Una prueba de JUnit 5 sin Spring, con PostgreSQL. Las dependencias de Maven son org.testcontainers:testcontainers-junit-jupiter y org.testcontainers:testcontainers-postgresql (desde la 2.0 todos los módulos llevan el prefijo testcontainers-, y la clase está en el paquete org.testcontainers.postgresql):

@Testcontainers
class ClientesRepositoryIT {

    @Container
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:18-alpine");

    @Test
    void guardaYRecuperaUnCliente() throws Exception {
        try (var conexion = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword())) {
            // crear la tabla, insertar, consultar y comprobar
        }
    }
}

Con Spring Boot es aún más corto. La anotación @ServiceConnection hace que Spring configure solo la conexión de la aplicación con el contenedor: no hay que escribir URL, usuario ni contraseña en ningún sitio. (Antes de que existiera había que copiar esos datos a mano con @DynamicPropertySource.)

@TestConfiguration(proxyBeanMethods = false)
class ContenedoresDePrueba {

    @Bean
    @ServiceConnection
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:18-alpine");
    }
}

Spring Boot permite además usar esa misma configuración para desarrollar: una clase con un main en la carpeta de pruebas arranca la aplicación con SpringApplication.from(MiAplicacion::main).with(ContenedoresDePrueba.class), y la base de datos aparece sola al ejecutarla desde el entorno de desarrollo.

Por convención, las pruebas de integración se nombran *IT y las ejecuta en Maven el plugin Failsafe (en la fase verify), separadas de las unitarias, que ejecuta Surefire. Así, quien no tiene Docker puede seguir pasando las unitarias.

Caso real: Kopi Chess

Kopi Chess guarda sus partidas en PostgreSQL con SQL escrito a mano (sin JPA) y prueba ese adaptador contra un PostgreSQL real con Testcontainers 2.x en Spring Boot 4. Su guía para contribuir lo dice claro: hace falta JDK 25 y Docker, porque las pruebas de integración usan Testcontainers.

  • Una configuración, dos usos: TestcontainersConfiguration declara el contenedor de PostgreSQL como bean con @ServiceConnection. La usan las pruebas de extremo a extremo (GameApiIT, AnalysisIT) y también TestKopiApplication, que arranca la aplicación para desarrollar sin ficheros de Compose ni bases de datos manuales: solo con Docker en marcha.
  • La misma imagen que en producción: la versión de PostgreSQL está fijada (postgres:18.6-alpine3.24) y un comentario recuerda mantenerla igual que en compose.yaml, el fichero con el que se ejecuta la aplicación.
  • Solo lo necesario: JdbcGameRepositoryIT no arranca toda la aplicación. Monta una mini aplicación con el adaptador de persistencia, la autoconfiguración de JDBC y Flyway (que aplica las migraciones del esquema) y el contenedor. Cada prueba empieza borrando las tablas.
  • Lo que solo se puede probar con el motor real: que una actualización con una versión antigua se rechace (el bloqueo optimista de la partida), que la propia tabla rechace una partida con un final imposible gracias a sus restricciones, y que la cola de análisis con FOR UPDATE SKIP LOCKED haga que un worker se salte el trabajo que tiene otro en vez de esperarlo (JdbcAnalysisJobQueueIT). Nada de eso se comportaría igual con una base de datos en memoria.
  • En la CI: GitHub Actions ejecuta ./mvnw verify, que pasa unitarias, integración y extremo a extremo; los ejecutores de GitHub ya traen Docker.

Errores frecuentes

  • Usar la etiqueta latest: las pruebas cambian solas cuando sale una versión nueva. Fija la misma versión que en producción.
  • Un contenedor por prueba: multiplica el tiempo. Compártelo por clase o por ejecución y limpia los datos entre pruebas.
  • Pruebas que dependen del orden: con un contenedor compartido, los datos de una prueba no pueden condicionar a otra. Borra o crea lo que necesites al empezar cada una.
  • Puertos fijos en la configuración: el puerto del equipo es aleatorio; pregúntalo al contenedor o deja que @ServiceConnection lo resuelva.
  • Usarlo para todo: la lógica de negocio se prueba mejor con pruebas unitarias y dobles, en milisegundos. Testcontainers es para los adaptadores que hablan con el servicio real.
  • Olvidar que la CI necesita Docker: sin él, las pruebas fallan al arrancar. Sepáralas con Failsafe para poder ejecutar las unitarias en cualquier sitio.
  • Copiar ejemplos de la 1.x en la 2.x: los nombres de las dependencias y los paquetes cambiaron, y JUnit 4 ya no está soportado.
